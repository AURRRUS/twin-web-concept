# Code Motion

## Определить результат

| Запрос | Результат |
|---|---|
| «Подготовь ТЗ», «промпт для разработчика» | Исполнимое ТЗ и timeline, без автоматического рендера видео. |
| «Сделай анимацию», «прототип», «HTML» | Самодостаточный HTML с preview/control; тест кадров. Экспорт MP4 только если запрошен. |
| «Создай ролик», «MP4», «HTML и видео» | ТЗ по необходимости, HTML, ключевые кадры, MP4, проверенные параметры экспорта. |
| «Для сайта», «scroll/reveal» | Спецификация interaction и рабочий web-модуль. Не подменять живой интерфейс видеороликом. |

Не спрашивать повторно разрешение на обычное создание кода и прямо запрошенный экспорт. При отсутствии критичных деталей использовать разумные явно отмеченные дефолты: offline 1920×1080, 60 fps, 6–12 секунд; длительность до 30 секунд как практический scope, не предел технологии. Если пользователь дал 30 секунд, считать 1800 кадров и не путать длительность ролика со временем вычислений. Не обещать 60 fps на всех устройствах или «работает в любой нейронке».

Перед реализацией определить аудиторию, сообщение, носитель, бренд, исходные факты/тексты/активы, длительность, размер, live/video, loop/once и звук. Не начинать новое продуктовое discovery при утверждённом brief.

## Зафиксировать источник стиля и фактов

Считать этот навык технологией, а не дизайн-системой. Для ПИН использовать `pinwebconceptsystem`; прочитать его действующий visual lock и [брендовый профиль ПИН](../skill-6aabf06bd7c08191ada4f6e94505f37b/references/brand-profile.md): Б/А, белая подпись действий, бронзовый веб и отдельный золотой носитель. Для собственного Twin читать [профиль Twin](../skill-6acac446d1208191b71aca5d93fa68a2/references/twin-brand.md): использовать актуальный реестр вариантов и разворот из профиля; старую нумерацию №01 не считать действующим выбором. Для Talent/ЖК использовать соответствующий брендбук/утверждённый концепт; профиль Twin действует только в согласованном модуле, не перекрашивает сайт клиента. Не переносить палитру, показатели, тексты и продуктовые обещания между ПИН и Talent.

Сохранять утверждённые CTA, числа, значения, статусы данных, права и продуктовую структуру. Считать анимацию раскрытием смысла, не поводом выдумывать факты. Показывать источник и статус финансовых данных; sample data помечать как демонстрационные. Не выдавать анимированную иллюстрацию строительства за документальный таймлапс.

Для движения типографики, UI, геометрии, графиков и иллюстративных таймлапсов использовать код. Для фотореалистичного облёта здания или людей не обещать равноценную замену 3D/video tools. По строгому условию «каждый кадр рисуется кодом» не использовать скрытую видеоподложку. Статические фото/официальные логотипы допустимы как явно оговорённые embedded assets; не считать их сгенерированными кодом.

## Подготовить исполнимое ТЗ

Читать [motion-spec.md](references/motion-spec.md). Выдать короткое описание идеи, источники/допущения, storyboard с абсолютными интервалами времени, точные строки/данные, траектории/маски/opacity/scale, easing, финальные состояния, responsive/reduced-motion и критерии QA. Для developer handoff задать интерфейс, размещение, trigger, состояния, выгрузку, интеграцию и ограничения; не ограничиваться «сделать красиво и плавно».

Не навязывать opening/main/closing интерактивному компоненту сайта. Для отдельного ролика использовать эту структуру, если она отвечает задаче. Не требовать нового события каждые 0.5 секунды механически: сохранять паузы для чтения и понимания. Easing выбирать осмысленно; не смешивать все функции из рекламного промпта. Для ПИН — restrained cubic/opacity/небольшой Y, без bounce/elastic и бесконечной суеты.

## Реализовать deterministic core

Читать [implementation.md](references/implementation.md). Использовать `assets/motion-template.html` как рабочий старт, адаптировать под brief, а не оставлять технический пример как готовый брендовый ролик.

Собрать один self-contained HTML: CSS/JS inline; шрифты/изображения data URI, если нужны; никаких CDN и внешних запросов для offline-файла. Хранить все контентные тексты, числа, style tokens, имена, размеры и scene timings в одном `window.CFG` в начале script. Использовать HTML/CSS для обёртки/типографики и Canvas 2D для внутренней сцены.

Экспортировать `window.ready` Promise для fonts/images и синхронный `window.render(t)` для точного времени в секундах. Один и тот же t всегда должен давать одинаковый кадр независимо от порядка вызовов; сбрасывать все DOM и Canvas состояния каждый render. Не использовать таймеры, CSS animations/transitions, Date.now, performance.now и несеяный random в render core. Seed randomness считать из CFG seed и стабильного id; не накапливать состояние симуляции.

Ожидать document.fonts.load для выбранных гарнитур и document.fonts.ready, проверить наличие нужного шрифта/кириллицы. При отсутствии коммерческого шрифта использовать явно отмеченную доступную sans-serif замену, не полагаться на имя SF Pro. Не задерживать отрисовку таймером «для загрузки шрифтов».

## Развести live и offline

Offline: render(t) вызывается внешним exporter на i/fps; screenshot каждого кадра, не запись экрана в реальном времени. Скорость рендера не меняет частоту экспортного видео.

Live: requestAnimationFrame допустим только во внешнем driver, передающем абсолютное t в тот же deterministic core. Scroll driver отображает scroll progress в t, не использует скрытый автономный таймер. При prefers-reduced-motion показывать информативное финальное/статическое состояние; не прятать контент. При внеэкранном/скрытом компоненте приостанавливать playback, сохранять корректное состояние.

В реальном сайте оставлять текст, данные и controls семантическим DOM; canvas-декор aria-hidden. Для смысловой canvas-инфографики дать DOM-summary/table, доступный с клавиатуры контроль, pause для продолжительного/autoplay motion; исключить вспышки и блокировку скролла. Не переносить весь сайт в canvas. Измерять стоимость frame на согласованном устройстве/viewport; budget около 16.7 ms для цели 60 Hz — план, не доказательство.

## Проверить и экспортировать

1. Проверить toolchain: Node/Playwright Chromium + ffmpeg/ffprobe. Не обещать MP4 до успешной проверки. При недоступности выдать HTML/ТЗ и честно указать недостающий компонент.
2. Выполнить `scripts/render_motion.cjs --html ... --out ... --mode preview`: ключевые кадры, отсутствие page errors, проверки repeat/out-of-order render. Осмотреть ключевые и переходные кадры, проверить clipping, spacing, данные, текст и бренд.
3. Для запрошенного видео запустить `--mode video`: i=0..N−1, t=i/fps, N=duration×fps. PNG sequence → ffmpeg H.264 MP4, constant fps, yuv420p, faststart. Требовать чётные размеры для yuv420p. Не добавлять лишний кадр при t=duration.
4. Проверить ffprobe: размеры, frame rate, codec/pix_fmt, duration и frame count. Полностью декодировать файл ffmpeg. Не выдавать 60 fps metadata за доказательство плавности движения; осмотреть transitions и промежуточные кадры.
5. Выдать HTML и MP4 при запросе, preview и ТЗ по scope. Указать actual export parameters, ограничения звука/alpha/цвета; MP4/H.264 не сохраняет alpha. Сохранить артефакты по правилам среды.

Renderer — воспроизводимый baseline: он не заменяет визуальную проверку, benchmark мобильных устройств и QA интеграции сайта. Для звука отдельно учитывать sync, разрешённые assets и отсутствие MP4 audio в дефолтном exporter. Для прозрачности согласовать подходящий формат вместо молчаливой потери alpha.
