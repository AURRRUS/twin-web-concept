# Сайт Twin — проектный адаптер
1. Определить режим и scope последней команды владельца; не выполнять визуальную задачу при запросе инфраструктуры или подготовки.
2. Найти `AURRRUS/twin-web-concept` и ветку из актуального задания. Прочитать `AGENTS.md`, `TWIN_START.md`, `.twin/START.md`, `.twin/state.json`. Старые main/canonicalBranch не являются автоматическим указанием на текущую работу. Сверить remote/HEAD и сохранить более свежие изменения.
3. В реестре различить workflowTask, siteCandidate, V1/V2 и опубликованную версию. Открыть их TASK/contract/REVIEW/RESULT/HANDOFF по scope. `.twin/project.json` и `.twin/v2/project.json` — ссылки, не независимые каноны.
4. Прочитать `.twin/DECISIONS.md`, `.twin/ROUTING.md`, DESIGN.md; для V2 — `V2_START.md`, `docs/v2/DECISIONS.md`, типографический канон по реестру и унаследованную действующую область ENGINEERING. Значения, источники, изображения и разрешение брать из их канона, не копировать в отдельные версии.
5. Web Production — главный координатор сквозной работы; Frontend Engineer — инженерный соавтор/исполнитель. Этот навык отвечает за проектные правила и ссылки Twin. Читать реальные SKILL/PROJECT_OVERRIDE; фактический запуск отдельного агента подтверждать ID/evidence.
6. RF Dewi, иерархия и контент наследуются из источников Twin; бренд ПИН не переносить. Заголовки без конечных точек. Точность реального объекта и его составляющих сохранять отдельно от адаптивной композиции.
7. Разрешение публикации candidate получать по publicationAuthority.source в реестре, ограничения текущей workflow-задачи учитывать отдельно. V2 выпускается только своим publisher с сохранением V1. Technical PASS, visual verdict, owner approval и deploy различать; не добавлять повторное согласование снимков к уже разрешённому выпуску.
8. Сохранить результат и следующий шаг в Git. Отсутствие инструментов назвать точно; не имитировать исполнения, независимость или публикацию. Промпт передачи показывать текстом.
