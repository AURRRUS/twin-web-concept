# Контекст, GitHub и Codex

## Возобновить работу
Перед задачей прочитать проектный AGENTS → единственный указатель активной задачи → профиль/решения → контракт → последний результат и открытые дефекты. Сопоставить с реальными remote/branch/commit и доступным runtime. Не выбирать ветку только по давнему слову canonical, не считать main автоматически рабочей версией.
Если указатели расходятся, определить актуальность по последнему решению и истории изменений; записать исправление в пределах задачи. Не откатывать свежий код к старому ТЗ. Старые документы помечать superseded с ссылкой на замену; не удалять доказательства и исходники без проверки зависимостей.
Закончить сессию записью: сделано, принято, не принято, текущая версия, изменённые файлы, пройденные проверки, открытые дефекты, следующий конкретный шаг. Это память проекта; история чата не является единственным хранилищем.

## Канонические данные
У проекта один короткий вход, один активный task pointer и один набор design tokens. У задачи один scope, один visual contract, один scene/asset manifest, один run/review и итог. Генерируемые сводки должны ссылаться на канон, а не хранить независимые копии запретов публикации или чисел типографики.
Записывать source commit и fingerprint фактических runtime-входов, контракта и reference. Изменение кода/медиа/шрифтов инвалидирует затронутую проверку; изменение отчёта без изменения runtime не требует выдуманного нового browser PASS. Новый SHA сам по себе не доказывает новый UI, совпавший SHA не доказывает проверку состояния. Для review хранить проверенный набор и evidence.
Версии навыков в GPT и репозитории сверять по manifest: name, источник/ревизия, hash содержимого, проектный override. Обновление personal skill не обновляет автоматически .agents/skills другого репозитория. При переносе сохранить только нужные инструкции/ресурсы и лицензии, исключить caches. Проектный адаптер хранит бренд и пути; общий workflow находится у Web Production.

## Реальная команда внутри Codex
Для существенной реализации конвейера явно поручить Codex запустить исполнителя и отдельного проверяющего; исследователь/графика/motion — по задаче. После завершения исполнителя проверяющему дать чистые исходные материалы и фактический результат. Разделить владение файлами, избегать параллельных правок одного CSS/компонента; общий merge делает ведущий Codex.
В начале проверить возможности текущей среды: запуск subagent, чтение изображений, browser, build, запись GitHub и deploy. Не путать конфигурацию роли, skill, GitHub workflow и реально запущенный агент. Сохранять agent/session ID, роль, scope, входную версию, выход и evidence. Если среда не предоставляет подагентов или визуальную проверку, назвать конкретный разрыв и перенести обязательство в GPT Work/другую доступную сессию. Авторская перепроверка остаётся self-review.
Проверенная документация 29.10.2026: https://learn.chatgpt.com/docs/agent-configuration/subagents . Для текущих локальных клиентов custom agents задаются отдельными .codex/agents/*.toml с name, description, developer_instructions. Версию клиента и поддержку проверить перед установкой; не добавлять неподдерживаемые ключи вслепую, не менять разрешения окружения. Инструкция «не редактировать» не создаёт отдельную read-only sandbox.

## Исполнимый пакет
Передать цель, task path, точную базу, scope/out-of-scope, порядок источников, необходимые материалы, ответственных, требования запуска агентов, проверки и условия выпуска. Не отправлять только фразу «как в предыдущем чате». Числа и критерии брать из канона, не переписывать в промпте второй раз.
Начало handoff: «Восстанови контекст из входа и активной задачи, сверив фактическую ветку. Примени Web Production как координатора и Frontend Engineer как инженерный контракт. Запусти назначенных исполнителя и независимого reviewer. Реализуй только указанный пакет; новые решения, defects и итог запиши рядом с кодом». Далее указать конкретные пути, branch/base, входы/выходы и критерии этой задачи.
Если внешний Codex не вызывается инструментом текущего сеанса, показать полный промпт и доступные файлы. Не заявлять «отправлено», если только подготовлена инструкция.

## Проверка и выпуск
Проверять код, который реально обслуживает маршрут. Тесты старого helper, не импортируемого компонентом, не принимают новую сцену. Проверки должны включать реальные состояния/ошибки/CTA и затронутые mobile/motion границы. Изображение сравнивать при том же viewport/state, движение — действием в браузере. Собирать и проверять один candidate; после изменения проверять затронутое.
Разделить технический статус, визуальный вердикт, решение оператора и deployment. Для preview с разрешёнными дефектами хранить конкретное разрешение/область/версию; не менять визуальный verdict ради загрузки. Финальная публикация сохраняет условия проекта. После разрешённого deploy проверять URL, маршрут, ассеты, исходную/опубликованную версии и поведение; push кода не равен обновлению сайта.
Работать с GitHub через доступный connector/CLI. Создать ветку/PR по scope, без force-push и удаления чужих изменений. Условия branch protection/доступов соблюдать; отсутствие доступа не скрывать. Не добавлять в репозиторий историю ZIP, node_modules, build caches и дубли больших render; при cleanup сначала проверить ссылки и назначение файлов. История Git сохраняется; purge/rewrite истории не входит в обычную уборку.

## Проверка самого конвейера
На Twin пройти один вертикальный пакет: сложная сцена + стык + mobile + один штатный CTA + независимая проверка + разрешённый preview. На PIN пройти отдельный пакет mobile/performance/конверсия. Начать следующую сессию с короткой командой продолжения и проверить восстановление принятых решений. Только после обоих пилотов считать процесс пригодным для клиентского повторения; обновлённые инструкции сами по себе не доказывают это.
