## W01. Зафиксированное направление

**Решения и намерения владельца из текущего обсуждения:**
1. Сайты для девелоперов двух видов: с Twin и без Twin.
2. Битрикс24 — наиболее частый CRM-сценарий.
3. Нужна собственная управляемая основа с контролем данных и возможностью сменить поставщика.
4. Шахматка — один из главных рабочих инструментов.
5. ИИ должен помогать с данными CRM, остатками, аналитикой лотов, ценообразованием и маркетингом.
6. Нужны GEO, возможные интерфейсы для ИИ и управление сайтом через ИИ.
7. В админке требуется пространство проекта с понятными запросами материалов и подготовкой базы ассистента.
8. Idalite — обязательный конкурентный ориентир.
9. Мобильные сценарии и управление проектной документацией должны быть проработаны явно.

**Проектное предложение:** общее ядро объединяет контент, предметные данные, документы, интеграции, аналитику и разрешённые действия. Публичный сайт, рабочая админка и Twin используют согласованные данные.

**BASE-01.** Независимость обеспечивается доступом к исходникам, базе, медиа, схемам и экспорту; провайдер моделей подключается через заменяемый слой. Полная независимость от технологий не обещается.

**BASE-02.** Начать с открытого CMS-ядра и собственных предметных модулей. Конкретная CMS пока не выбрана. У интерфейсного шаблона админки нет автоматически backend, прав, публикаций и медиапроцессинга.

**BASE-03.** Отделять сайт, коммерческую систему и модуль Twin в архитектуре, смете и договоре. Не включать всё обсуждённое в стоимость обычного сайта по умолчанию.

WEB/WEB+TWIN — два вида клиентских сайтов. OPS и AI-KNOWLEDGE — уровни комплектации, а не третий и четвёртый вид сайта.

**CFG-01.** Для проекта явно перечислить включённые функции и зависимости. Отключённый модуль не оставляет фиктивных кнопок и ложного успеха.

| Роль | Основная задача | Результат |
|---|---|---|

| РОП/коммерческий руководитель | Управлять остатками и условиями | Согласованные действия и контроль результата |
| Контент-менеджер | Поддерживать материалы и знания | Актуальные страницы, галереи и источники |

**FLOW-01. Покупатель:** вход → понимание проекта → выбор → сравнение → уточнение → сохранение/обращение → продолжение с менеджером. Дать путь пользователю, который ещё не готов оставить контакт.

**FLOW-02. Маркетолог:** новый материал/сигнал → проверка источника → правка/гипотеза → предпросмотр → согласование → выпуск → измерение.

**FLOW-03. Коммерческий руководитель:** группа лотов → спрос/остатки/история → сценарий → проверка исключений → согласование → запись в ответственный источник → контроль публикации.

**FLOW-04. Документы:** поступление → классификация → извлечение → проверка → утверждение → использование → сравнение версии → задачи обновления → архив.

**FLOW-05.** В каждом переходе сохранять проект, объект, фильтры, выбранную подборку и допустимый контекст. Сбор контакта не должен прерывать каждую проверку характеристик без отдельного бизнес-решения.

## W06. Модель данных и ответственность

### W06.1. Сущности

Организация/клиент → проект → очередь/этап → корпус → секция/подъезд → этаж → лот. Необязательные уровни зависят от проекта. Отдельно: планировка, тип продукта, предложение, прайс, акция, резерв, обращение, CRM-сделка, медиа, документ, факт, источник, событие, набор изменений.

Гостиничный профиль описывает физический лот, повторяемую планировку и коммерческий тип номера отдельно. Вместимость, категории и характеристики подтверждаются клиентом; правила другого проекта не копируются автоматически.

**DATA-01.** Один внутренний ID лота используется в каталоге, шахматке, аналитике и Twin. Внешние ID хранятся в таблице соответствий с системой и областью клиента.
**DATA-02.** Номер квартиры, название корпуса и адрес не считать глобальными уникальными ключами.
**DATA-03.** Для денег хранить валюту, единицы, базу цены и период действия; точную арифметику выполнять подходящим числовым типом. Различать полную цену и цену за м².
**DATA-04.** Различать отсутствующее значение, ноль, неприменимость и ошибку загрузки.
**DATA-05.** Хранить историю доступности и цен с временем действия и временем поступления; отдельно договорные условия конкретной сделки.

### W06.2. Источники

| Тип | Ответственный источник по умолчанию |
|---|---|
| Страницы, галереи, статьи | CMS |
| Факты о проекте | Подтверждённые документы/паспорт по политике поля |
| Цена, доступность, резерв | Назначенная система коммерческого учёта |
| Контакт, сделка, задачи | Битрикс24 либо CRM внедрения |
| Пространственная связь | Проверенная карта объектов Twin/2D |
| Метрики | Версионированный сервис аналитики |

**DATA-06.** Внедрение назначает источник для каждого управляемого поля. Локальное исправление не должно запускать бесконечный обмен и перезаписывать источник без правила.

## W07. Дизайн и визуальная система

**DES-01.** Бренд клиента первичен для клиентского сайта. Модуль Twin имеет согласованное оформление; он не перекрашивает весь сайт.
**DES-02.** Зафиксировать токены цвета, типографики, интервалов, размеров, слоёв, скруглений и motion. Реализовать общие примитивы кнопок, полей, диалогов, уведомлений.
**DES-03.** Создать партитуру всей страницы до фрагментарного украшения hero. Смысловая глава не обязана становиться отдельной горизонтальной полосой.
**DES-04.** Проверять нижнюю часть сайта на ту же проработку, что первый экран. Выбор/действие — полноценная сцена.
**DES-05.** Точные логотипы, планировки и утверждённые рендеры брать из оригиналов. AI-изображение не является технически точной схемой.
**DES-06.** Поддержка тёмной темы включается решением профиля; универсальное ядро использует семантические токены, но второй визуальный режим не добавляется автоматически.
**DES-07.** Ключевые состояния и mobile показывать отдельными макетами или рабочим прототипом. Desktop-растр не является макетом адаптации.

## W08. Motion и интерактив

**MOT-01.** Карточка эффекта: цель, триггер, начальное/конечное состояние, диапазон скролла или длительность, обратный ход, mobile, keyboard, reduced-motion, fallback, стоимость загрузки.
**MOT-02.** Текст, данные и управление остаются доступными в DOM. Canvas/WebGL/видео используются по назначению.
**MOT-03.** Не блокировать чтение и CTA заставкой; не перехватывать скролл для декоративного эффекта.
**MOT-04.** У reduced-motion содержательная статическая композиция. Выключение анимации не скрывает контент.
**MOT-05.** Вне экрана/скрытой вкладки останавливать ненужную работу. На mobile допустима другая механика при сохранении содержания и действия.
**MOT-06.** Prompt Motion — дополнительный референс механик: https://prompt-motion.com/. Для переноса фиксировать конкретный эффект и его задачу. Условия использования конкретного кода/ассета проверять перед включением; доступность сайта не доказывает лицензию на всё.
**MOT-07.** Кодовый deterministic render(t) нужен при соответствующем экспорте/сцене; не навязывать его каждому переходу обычного сайта. Ролик не заменяет интерфейс.
**MOT-08.** Для фотореалистичной архитектурной камеры нужны согласованные исходники и подходящий 3D/video-процесс. Не обещать точное восстановление пространства по произвольному растру.

## W09. Мобильная адаптация — обязательная самостоятельная часть

Владелец: UX/Frontend Lead. Вход: сценарии W03 и визуальная система. Выход: работающий покупательский mobile и определённый mobile-объём админки. Проверка: W27, сценарии T01–T20.

### W09.1. Диапазоны и базовые правила

**MOB-01.** Порядок реализации по решению владельца: сначала desktop с дизайном, затем отдельный этап мобильной адаптации. При проектировании desktop сразу учитывать reflow, семантику и будущие mobile-состояния, чтобы не переделывать архитектуру. Прежнее предписание mobile-first заменено этим решением; Контрольные ширины в CSS px: 320, 360, 390, 430, 768, 1024, 1440. Это тестовые точки, а не обязательные CSS breakpoints; фактические переломы определяет содержимое.
**MOB-02.** Публичный путь работает в портретной ориентации. Не требовать повернуть телефон ради сайта, каталога, документов или обращения.
**MOB-03.** Обычная страница не прокручивается по горизонтали. Двумерная шахматка/схема может иметь локальный pan/scroll с явной областью и альтернативным списком. Не маскировать ошибки общим overflow-x:hidden.
**MOB-04.** Текст масштабируется; не отключать пользовательский zoom. Проверять reflow при эквиваленте 320 CSS px, исключения — по назначению двумерного контента [S01].
**MOB-05.** Основные touch-элементы проектировать около 44×44 CSS px или больше как наше правило удобства. Минимум WCAG 2.2 AA — 24×24 с установленными исключениями; не выдавать 44 за универсальную норму AA [S02].
**MOB-06.** Hover не является единственным способом увидеть цену, статус, подсказку или действие. Есть tap/focus-путь.
**MOB-07.** Учесть safe-area, динамическую высоту viewport, экранную клавиатуру, системные панели, ориентацию и увеличенный текст.
**MOB-08.** Sticky-панели, cookie-баннер и чат не перекрывают друг друга, фокус, ошибки формы и основное действие. Нижний отступ соответствует реально занятому месту.

### W09.3. Шахматка на телефоне

**MOB-09.** Не уменьшать весь корпус до нечитаемой сетки. Дать контролируемую область, масштаб, подписи и действие «Показать списком».
**MOB-10.** Статус различается подписью/обозначением, а не только цветом. Закрепление осей не перекрывает ячейки.
**MOB-11.** Tap выбирает объект, карточка показывает цену/статус/актуальность. Возврат сохраняет позицию и выбранную секцию.
**MOB-12.** Для плотной сетки предусмотреть эквивалентный доступный список; все действия доступны без точного попадания в микроскопическую клетку.
**MOB-13.** Массовая операция открывает отдельное резюме выбранных объектов и последствий. Случайный tap не меняет прайс.

### W09.4. Формы, чат и документы

**MOB-14.** inputmode/autocomplete и тип поля соответствуют задаче; есть постоянные подписи. Клавиатура не закрывает активное поле и отправку.
**MOB-15.** При сбое сохранять введённое, показывать состояние доставки, позволять безопасный повтор. Возврат из приложения телефона/мессенджера не обнуляет выбор.
**MOB-16.** Чат не читает текущий лот по старому состоянию после перехода. В ответе видна область контекста; запоздалый результат не применяется к новому объекту.
**MOB-17.** Просмотр PDF имеет альтернативу «Скачать»/«Открыть оригинал». Таблицы и страницы можно увеличить; не обещать OCR-сводку как замену оригинала.
**MOB-18.** Мобильная загрузка принимает файлы из доступного системного выбора; фото документа допускается как материал на проверку, не как автоматически подтверждённый оригинал.

### W09.5. Слабая сеть, прерывание и эксплуатация

**MOB-19.** Публикация, импорт и генерация — фоновые задачи с ID и состоянием. После возврата показывается фактический результат, повтор не создаёт дубли.
**MOB-20.** Offline-доступ к кешу имеет маркировку; актуальность цены/наличия перепроверяется. Новая бронь offline не подтверждается.
**MOB-21.** Прерванная загрузка поддерживает безопасный повтор; возобновление крупных файлов — при выбранной инфраструктуре. Не терять уже успешно принятые файлы.
**MOB-22.** При отказе WebGL или недостатке ресурсов работает каталог/список/планировка. Запуск Twin не является условием обращения.
**MOB-23.** Для mobile-админки обязательны просмотр данных, проверка источника, простая правка, загрузка материалов и согласование. Сложная конфигурация и массовая переоценка могут иметь desktop-редактор; на mobile сохраняются понятный статус, объяснение и безопасный выход.

### W09.6. Обязательная проверка

iOS Safari и Android Chrome на реальных доступных устройствах; desktop Chromium и другие браузеры целевой матрицы. Проверить portrait/landscape без обязательного поворота, клавиатуру, увеличение текста, медленную сеть, потерю связи, системный Back, сворачивание/возврат. Эмуляция дополняет реальные устройства, а не доказывает их проверку.

## W10. Общая модель состояний и доступность

**STATE-01.** Компоненты покрывают применимые состояния: default, hover, focus-visible, active, disabled, loading, error, selected. Сценарии дополнительно: empty, success, permission-denied, stale, partial, conflict, offline. N/A допустим с причиной.
**STATE-02.** Loading не выдаёт старое значение за свежее. При partial видно, что загружено и что недоступно.
**STATE-03.** Диалог получает доступное имя, правильную семантику, управляемый фокус и возврат фокуса. Для модального режима фон недоступен взаимодействию; Escape/закрытие согласованы с сохранением данных.
**STATE-04.** Проверять клавиатуру, экранный диктор, контраст, видимый и не перекрытый фокус, порядок чтения и отсутствие цветового единственного кодирования.
**STATE-05.** Ошибки привязаны к полям и объясняют исправление. Уведомление об успехе соответствует фактически завершённой операции.
**STATE-06.** Предпросмотр групповой или денежной операции показывает объект, старое/новое значение и последствия. Дополнительная защита соразмерна действию; не требовать ввод текста при любой обычной правке.

Цель доступности — WCAG 2.2 AA в согласованном объёме. Автоматический аудит не заменяет ручной проверки. Реализованный контраст измеряется; в этой спецификации измерений интерфейса ещё нет.

<a id="w12"></a>
## W12. Каталог, подбор и карточка лота

Владелец: Product + каталог/CRM. Вход: W06 и источник коммерции. Выход: выбор, сравнение, обращение.

**CAT-01.** Фильтры соответствуют доступным данным: тип, бюджет, площадь, комнаты/категория, корпус, этаж и подтверждённые свойства. Неприменимые параметры не показываются.
**CAT-02.** Применённые фильтры, сортировка и количество результатов видны. Прямая ссылка воспроизводит допустимое состояние.
**CAT-03.** «Нет подходящих вариантов» предлагает изменить условия; не подменяется ошибкой сети.
**CAT-04.** Планировка, коммерческий тип и физический лот связаны, но не смешиваются.
**CAT-05.** Карточка показывает идентичность, существенные характеристики, цену/статус с применимостью, материалы, действие и альтернативы.
**CAT-06.** Подборка хранит ID и предпочтения. При открытии перепроверяются актуальные условия; сохранённый снимок не выдаётся за текущий прайс.
**CAT-07.** Покупательский поиск через ИИ формирует понятные пользователю критерии. Уточнение вручную остаётся доступным.
**CAT-08.** История интереса хранится отдельно от итогового предмета сделки. Покупатель может смотреть несколько лотов.

<a id="w13"></a>
## W13. Шахматка — публичная и рабочая

Владелец: коммерческий руководитель + Product. Зависимости: ID, источник остатков, W14, W22. Публичный и внутренний режимы имеют разные поля и права.

### W13.1. Режимы

| Режим | Содержание | Действие |
|---|---|---|
| Доступность | Согласованные статусы | Выбор/запрос, разрешённая операция |
| Цены | Действующий прайс и история | Сценарий изменения |
| Спрос | Просмотры, сохранения, обращения | Сравнение сопоставимых групп |
| Воронка | Сделки, этапы, исходы | Анализ с переходом по правам |
| Остатки | Состав, экспозиция, время доступности | Приоритеты и контроль |
| Сценарий | Предлагаемые условия и исключения | Проверка и согласование |

**CHESS-01.** Внутренняя клетка и публичная карточка ссылаются на тот же лот. Внутренние комментарии, клиенты и стратегия цен не входят в публичный API.
**CHESS-02.** Модель статусов настраивается по внедрению. Пример: недоступен для продажи, свободен, резерв, бронь, продан. «Есть обращение» не является статусом брони.
**CHESS-03.** Для перехода задаются инициатор, условия, срок, ответственный источник, отмена и журнал. Бронь с истечением срока требует отдельной серверной логики.
**CHESS-04.** В запросе на изменение передавать ожидаемую версию. При конкурентном изменении показывать конфликт, не затирать данные.
**CHESS-05.** Групповая операция имеет предварительный результат и пообъектный отчёт. Частичное выполнение не отображается как полный успех.
**CHESS-06.** У аналитической раскраски видны метрика, период, объём выборки и легенда. Нулевой спрос отличается от отсутствия измерения.
**CHESS-07.** Производительность проверяется на согласованном размере каталога. Виртуализация сохраняет клавиатурный и альтернативный доступ.
**CHESS-08.** Mobile — MOB-09–MOB-13; глобально уменьшенная desktop-сетка не принимается.

<a id="w14"></a>
## W14. Битрикс24 и интеграции

Владелец: Integration Lead/CRM-администратор. Результат: достоверный обмен и видимый контроль состояния.

**CRM-01.** В каждом внедрении фиксируются режим Битрикс24, доступные методы, роли, сущности, поля, лимиты и используемые приложения. «Подключён Битрикс24» не означает готовый каталог недвижимости.
**CRM-02.** Для обращения передавать проект/лот/подборку, сообщение, допустимые контактные данные, источник страницы и согласованные UTM. Правила создания контакта, лида и сделки определяются конфигурацией.
**CRM-03.** Сервер хранит обращение и ID доставки, защищает повтор от дублей и показывает pending/delivered/failed. Пользовательский успех означает конкретный уровень: запрос принят системой либо доставлен в CRM.
**CRM-04.** События изменений дополняются периодической сверкой. Порядок и повтор событий не предполагаются гарантированными.
**CRM-05.** Обмен использует таблицу соответствий ID. Неоднозначное AI-сопоставление требует проверки.
**CRM-06.** Секреты находятся на сервере. Для интеграции нужны минимальные права и отзыв доступа.
**CRM-07.** Страница диагностики показывает время последнего успеха, очередь, ошибки и ответственного. Импорт с ошибкой не обнуляет каталог.
**CRM-08.** Перед реальной бронью/сменой цены проверять актуальное состояние ответственного сервиса. Две независимо обновляемые базы не образуют общей транзакции.

REST-документация Битрикс24 описывает смарт-процессы и события [S09]. Проектирование поля «лот» и надёжного процесса — наша работа, а не встроенное следствие наличия REST.

## W15. Остатки и ценообразование

**PRICE-01.** Разделить базовую цену, прайс, скидку, акцию, индивидуальные условия и зафиксированную цену сделки.
**PRICE-02.** В расчёте явно заданы валюта, округление, применимость, дата начала/окончания и исключения. Исполнитель использует проверенный код.
**PRICE-03.** Сценарий показывает выбранные лоты, старое/новое значение, изменение общей стоимости экспозиции и допущения.
**PRICE-04.** Изменение прайса не переписывает договорную историю.
**PRICE-05.** Рекомендация ИИ включает данные, ограничения, гипотезу и проверку. «Просмотров много, сделок мало» не доказывает необходимость скидки.
**PRICE-06.** Прогноз эластичности/скорости продаж — отдельная модель и валидация. Языковая модель не придумывает её коэффициенты.
**PRICE-07.** Автоматическая переоценка — ОПЦИЯ с лимитами, правилами, журналом и выключением. На первом этапе — расчёт и согласование.
**PRICE-08.** Любая запись из админки, ИИ и интеграции проходит одинаковые серверные ограничения.

<a id="w16"></a>
## W16. CMS, медиа, галереи и публикации

Владелец: маркетинг/контент. Выход: самостоятельное обновление без разрушения композиции.

**CMS-01.** Редактор работает со структурированными блоками и разрешёнными вариантами. Произвольный HTML/JS не является штатным полем маркетолога.
**CMS-02.** Поддержать черновик, предпросмотр настоящего frontend, выпуск, историю и восстановление. Пакет взаимосвязанных изменений выпускается согласованно.
**CMS-03.** Блог, новость и кейс могут иметь разные модели. Поля: заголовок, анонс, автор, рубрика, даты, материалы, связи и SEO.
**CMS-04.** Плановая публикация и завершение акции учитывают часовой пояс проекта, ошибки и статус фоновой задачи.
**CMS-05.** Мобильный предпросмотр обязателен перед изменением ключевого медиа; это не заменяет проверку реализации.

**MEDIA-01.** У ресурса постоянный ID, оригинал, технические варианты, тип, подпись, alt по назначению, права использования, связи и версия.
**MEDIA-02.** Пакетная загрузка, порядок, обложка, теги, поиск и список мест использования.
**MEDIA-03.** При замене выбор: глобально либо новый ресурс. Показать затрагиваемые страницы; запретить незаметное удаление используемого оригинала.
**MEDIA-04.** Поддержать mobile-crop, точку фокуса, responsive-варианты, прозрачность для соответствующих форматов. Содержание объекта не менять обработкой без задания.
**MEDIA-05.** Фасад/генплан и интерактивные зоны версионируются связкой. Замена изображения требует проверки координат и соответствия ID.
**MEDIA-06.** Ход строительства связан с проектом/корпусом, датой съёмки и периодом публикации. Фото, схема и рендер различаются.
**MEDIA-07.** Новая версия обновляет необходимые кеши и производные изображения. Старые ссылки и исторические публикации обрабатываются по политике.

## W17. SEO, GEO и внешние ИИ-каналы

## W20. Единое управление и оркестрация документов

Владелец: документ-контролёр + Product/AI Lead. Результат: версия документа → подтверждённые факты → зависимые страницы/ответы/задачи.

### W20.1. Реестр

**DOC-07.** Карточка хранит: document_id, project_id, класс, точное название, номер, издателя/автора, охват, даты, язык, формат, размер, checksum, источник, версию, статус, владельца, доступ, срок проверки, связи replaces/amends и расположение оригинала.

**DOC-08.** Оригинал сохраняется неизменяемым. OCR, текст, фрагменты, таблицы, превью и сводки — производные материалы со своими версиями обработки.
**DOC-09.** Подпись/печать, видимая на скане, не считается проверенной электронной подписью. Статус криптографической проверки хранится отдельно при наличии функции.
**DOC-10.** Дедупликация по байтам не объединяет автоматически документы разных объектов. Одинаковое название не доказывает идентичность.

### W20.2. Обработка и состояния

Приём → проверка файла → классификация → OCR/извлечение → привязка → проверка фактов → согласование применимости → разрешение использования → мониторинг.

Состояния документа: received, processing, needs_review, approved_for_use, conflict, stale, superseded, revoked, failed. Отдельно состояния публичной публикации и разрешений ИИ. «Разрешён ИИ» не означает «опубликован на сайте».

**DOC-11.** Каждый этап — возобновляемая задача с ID, версией исходника, результатом и ошибками. Отказ на одной странице не создаёт фиктивно полный документ.
**DOC-12.** Таблицы сохраняют строки, столбцы, единицы и связь с объектом. Для важного числа виден исходный фрагмент.
**DOC-13.** Ассистент ссылается на документ, версию, страницу/раздел или ячейку. Для скана — страницу/область.
**DOC-14.** Сведения получают статусы: извлечено, проверено, конфликтует, неприменимо, устарело. Уверенность распознавания не заменяет подтверждение.

### W20.3. Новая версия и влияние

Новый документ → проверка охвата → техническое и смысловое сравнение → кандидаты изменений → граф зависимостей → задачи ответственным → согласованный выпуск.

**DOC-15.** Новая дата загрузки не устанавливает юридический приоритет. Политика поля учитывает источник, редакцию, применимость и период.
**DOC-16.** Например, изменившийся срок передачи создаёт проверку паспорта, страницы, FAQ и сценариев ответа. Дата выдачи разрешения не подменяет срок передачи.
**DOC-17.** Семантическое сравнение ИИ — подсказка. Коммерческие/официальные изменения подтверждает соответствующий ответственный.
**DOC-18.** Согласованный пакет хранит before/after, основания, проверяющего, версии и зависимые публикации. При изменении основания между проверкой и выпуском — повторная проверка.
**DOC-19.** Отзыв/замена источника обновляет поиск, кеши и производные факты. Уже сохранённый старый ответ остаётся историческим с отметкой, а не превращается в новый факт.
**DOC-20.** Автоматическое получение внешних документов — ОПЦИЯ после проверки доступного интерфейса и условий. 403 не означает пустой источник. Для пилота допустима контролируемая ручная загрузка со ссылкой и датой сверки.

## W30. Связь с текущей разработкой Twin

### W30.1. Корпоративный сайт Twin

Последние решения текущего обсуждения имеют приоритет над историческими бренд-профилями:
- позиционирование — цифровая инфраструктура продаж;
- коммерческий цифровой двойник — ядро;
- виртуальный отдел продаж — операционный слой;
- рабочая визуальная концепция — белая основа и связанная архитектурная история;
- G выбран для примерки сайта; это не утверждение о готовом production-master логотипа;
- карта состава — ядро и шесть компонентов; функции отдельного лота не подменяют верхний уровень состава;
- отменённые формулировки не восстанавливать из старых материалов.

**TWIN-01.** Существующий frontend-handoff описывал первый демонстрационный проход без CMS/backend/настоящей CRM. Настоящий master добавляет стандарт следующих объёмов, не объявляет их реализованными и не изменяет старую смету.
**TWIN-02.** Визуальные детали корпоративного Twin не становятся обязательным дизайном всех клиентских сайтов.

## W35. Корпоративная ИИ-среда: агенты, задачи и обратная связь

### W35.1. Направление и границы
Статус: направление предложено владельцем; нижеследующие механизмы — проектная спецификация. Публичный сайт, внутреннее пространство команды и фоновые задачи используют общие сущности проекта с разными правами. Это развитие W18–W24; функции не объявляются реализованными и не входят автоматически в любой сайт.

| Контур | Назначение | Данные |
|---|---|---|
| Публичный | Консультация, подбор, сравнение, выбор в Twin, обращение | Только разрешённые публичные сведения и коммерческие данные |
| Внутренний | Документы, контент, анализ, подготовка действий | Данные организации/проекта по правам сотрудника |
| Фоновый | Проверки, отчёты и процессы по расписанию/событию | Отдельная служебная роль с ограниченным доступом |

**CORP-01.** Общие данные не означают общий доступ. Проверять права до поиска и вызова инструмента; внутренние диалоги, документы и CRM не переходят в публичную базу автоматически.
**CORP-02.** Начать с одного оркестратора и ограниченного набора инструментов. Ролевой профиль не требует отдельной модели/процесса; делегирование нескольким агентам вводить после измеримой пользы.
**CORP-03.** Реестр агента: agent_id, версия, назначение, аудитория, scope проекта, источники, инструменты, выходная схема, запрещённые действия, лимиты, тесты, ответственный, статус. Новая инструкция не расширяет серверные права.

### W35.3. Автозадачи как функция будущей системы
Это спецификация собственного планировщика, не запрос создать задачи в текущем ChatGPT.

**AUTO-01.** Задание задаёт trigger (расписание/событие/условие), timezone, область, владельца, agent/version, схему входа, разрешённые инструменты, бюджет, timeout, правила повторов, выход и способ уведомления. Каналы доставки подключаются по полномочиям; сам факт расписания не даёт права отправлять сообщения клиентам.
**AUTO-02.** Состояния: draft → enabled → queued → running → succeeded/partial/failed/cancelled; paused для отключённого расписания. Разрешённое изменение может дополнительно иметь awaiting_review. Уведомление, подготовка результата и исполнение — разные действия.
**AUTO-03.** Использовать уникальный ключ запуска/события, запрет нежелательного перекрытия, ограниченные повторы и журнал. После перерыва исполнять пропущенные запуски только по явно заданной политике catch-up. Смена часового пояса/времени учитывается в расписании.
**AUTO-04.** При запуске и перед записью перепроверять доступ и версии. Согласование привязано к конкретному набору изменений; устаревший набор требует пересчёта. Фоновая роль не наследует автоматически права создателя.
**AUTO-05.** В админке доступны пауза, отмена, история, частичный результат, причина ошибки и повтор. Остановка не отменяет уже выполненные внешние действия; нужна компенсация по W28.
**AUTO-06.** Начальный режим — чтение/черновики/рекомендации. Публикация, изменение цены/остатка, создание брони и внешний контакт разрешаются отдельно по типу действия. Это предлагаемая политика внедрения, не запрет владельцу настроить иной уровень автоматизации.

Примеры: еженедельные вопросы без ответа; проверка источников после новой версии документа; расхождения каталога и CRM; анализ групп лотов при достаточной выборке. Конкретная частота, пороги и получатели задаются профилем внедрения.

### W35.4. Обратная связь от покупателей
**FEED-01.** Связывать запрос с этапом, контекстом выбранных объектов, результатом ответа и действием пользователя в разрешённых пределах. Удалять лишние персональные данные; цели и сроки использования определить до сбора.
**FEED-02.** Обращение покупателя — наблюдение. Реестр улучшений хранит issue_id, период, нормализованную тему, счётчик уникальных обращений и знаменатель, обезличенные примеры, качество ответа, возможную причину, затронутый сценарий, предложение, сложность, владельца и статус.
**FEED-03.** Исключать ботов/тестовые сессии, повторные сообщения одного разговора не считать независимыми покупателями. При малой выборке показывать ограничение; не придумывать порог достоверности.
**FEED-04.** Цепочка: наблюдение → разбор причины → гипотеза → приоритизация → эксперимент/задача → проверка. Частый вопрос о сроке сдачи может требовать улучшить видимость существующего ответа, а не новую функцию.
**FEED-05.** Ассистент создаёт предложение в backlog, а не молча меняет roadmap, исходные документы, оффер или интерфейс. Принятое изменение получает ID и проверку результата; гипотеза не становится подтверждённой от факта её реализации.

### W35.5. Приёмка и экономика
**CORP-QA-01.** Проверить: чужой проект; отзыв прав в очереди; противоречивый источник; повтор события; устаревшее согласование; частичный отказ; исчерпание бюджета; остановка; недоступная модель. Публичный сайт продолжает основные операции.
**CORP-QA-02.** Измерять успешно выполненные задачи, фактическое время сотрудника, долю исправлений, стоимость результата и полезность принятых предложений. До пилота не обещать рост продаж или экономию.
**CORP-QA-03.** Начальный пилот: один проект, одна внутренняя роль, один публичный сценарий, одна фоновая задача чтения. Это рекомендуемая комплектация; запускается отдельными пакетами W36 после готовности данных.

<a id="w36"></a>
## W36. Разработка частями: пакеты, зависимости и передача

### W36.1. Закон исполнения
**PIPE-01.** Master — карта продукта и стандарт, не единое задание «реализовать всё». Разработчик получает профиль проекта и одну карточку текущего пакета. Смежные разделы читаются по зависимости; все файлы архива не превращаются в scope.
**PIPE-02.** Пакет заканчивается наблюдаемым результатом: экраном/сценарием, проверенной интеграцией или документированным контрактом. Если результат нельзя проверить отдельно или он скрывает несколько разных рисков, пакет разделить.
**PIPE-03.** В одном пакете сохранять вертикальный путь: необходимые UI, данные, состояния и проверка в пределах текущего этапа. Desktop, затем mobile — отдельные этапы по решению владельца; mobile-пакет использует те же сущности и компоненты, а не независимую копию сайта. Не строить весь frontend заранее, оставляя обработку ошибок и интеграции «на потом». Временные заглушки явно маркируются.
**PIPE-04.** Рабочие статусы: queued → ready → in_progress → verified → integrated; blocked/deferred для остановки. `verified` требует доказательств, `integrated` — включения в общую сборку. Production release — отдельный статус/действие, не следствие завершения пакета.

### W36.2. Обязательная карточка пакета
| Поле | Содержание |
|---|---|
| work_package_id / version / status | Устойчивый ID и состояние |
| goal / user_outcome | Одна проверяемая задача пользователя |
| requirements | ID требований master и профильных спецификаций |
| dependencies / input_versions | Предыдущие результаты, данные и версии контрактов |
| in_scope / out_of_scope | Что выполняется сейчас и что остаётся дальше |
| deliverables / allowed_changes | Код/экран/контракт и допустимые области изменений |
| states / mobile / accessibility | Обязательные состояния и способы взаимодействия |
| acceptance / evidence | Действия проверки и ожидаемый результат |
| integration / rollback | Как включается в общую сборку и отключается при отказе |
| blockers / next | Что реально мешает и какой следующий пакет готов |

**PIPE-05.** Оценивать работу после подготовки карточки; не обещать одинаковую длительность пакетов. В реестре отслеживать зависимости и незакрытые риски, а не процент строк кода.

### W36.3. Цикл одного пакета
Прочитать входы → проверить зависимости → реализовать ограниченный путь → проверить desktop/mobile/ошибки → исправить → зафиксировать результат и версии → обновить реестр и handoff. Не переписывать принятые части вне необходимости текущего пакета.

**PIPE-06.** После verified можно самостоятельно переходить к следующему ready-пакету, если пользователь поручил соответствующий этап. Это не требование получать подтверждение на каждый блок. При запросе на один пакет закончить им. Новые коммерческие решения и внешний выпуск не выводятся из разрешения на разработку.
**PIPE-07.** Если зависимость отсутствует, blocked получает только зависимый пакет. Независимая работа продолжается; заглушка не закрывает проверку реальной интеграции.
**PIPE-08.** При передаче в новый тред/сессию оставить checkpoint: commit/версия файлов, реализованные ID, реальные проверки, команды запуска, открытые ошибки, текущая карточка и следующий готовый пакет. Без секретов. Не начинать заново и не полагаться только на память чата.
**PIPE-09.** Принятые контракты/схемы версионируются. Изменение связывает затронутые пакеты, совместимость и релевантную регрессию. Проверять основную цепочку после каждого включения; полный набор повторять по риску, а не ритуально.

### W36.4. Порядок владельца: desktop → mobile → админка → ИИ

Статус последовательности: OPERATOR_CONFIRMED, 18.10.2026. Названия пакетов и детализация ниже — рабочая спецификация. Подключение готового Twin и базовых публичных интеграций относится к выбранному релизу сайта; пользователь не должен ждать внедрения ИИ ради работающей формы или счётчика.

| Этап / пакет | Проверяемый результат | Условие перехода |
|---|---|---|
| Подготовка / TW-00 | Карта исходников, контракт контента/интеграций, профиль и карточка первого блока | Входы и блокеры описаны |
| Desktop / TW-D01 | Каркас, header/hero, токены | Композиция и действия проверены на desktop |
| Desktop / TW-D02 | Архитектурная история | Сохранены ритм и пространственная композиция |
| Desktop / TW-D03 | Карта состава, диалоги и каналы | Доступны состояния и навигация |
| Desktop / TW-D04 | Оболочка демо, fixture и подключение viewer при готовности | Статус реального подключения явно указан |
| Desktop / TW-D05 | Форма, публичные интеграции, motion и desktop-регрессия | Принят desktop выбранного объёма |
| Mobile / TW-M01 | Header, hero, сцены и карта на малых экранах | Контент и действия читаемы/доступны |
| Mobile / TW-M02 | Демо, диалоги, форма, клавиатура/жесты/Back | Выбор и контекст сохраняются |
| Mobile / TW-M03 | Устройства, слабая сеть, итоговая сквозная приёмка | Публичный релиз может быть рассмотрен |
| Админка / TW-A01 | Одна CMS-страница: изменить → preview → выпустить → восстановить | Выбраны CMS и контентный контракт |
| Админка / TW-A02 | Медиа, документы, каталог и раздел интеграций — отдельными карточками | Для каждого модуля приняты права/ошибки |
| ИИ / TW-I01 | Проверенная база и одна внутренняя задача | Источники/права/качество проверены |
| ИИ / TW-I02 | Публичный консультант на разрешённых данных | Проверены ответы и инструменты |
| Автоматизация / TW-I03 | Одна фоновая задача и реестр предложений улучшений | Есть лимиты, аудит и отключение |

Каждый ряд — отдельное задание; крупные TW-A02 и TW-I01 дополнительно делятся по W36.2. Перечень не передаётся как команда «собери всё». Связи со старой черновой нумерацией TW-01…11 не являются начатой разработкой: новая таблица заменяет тот план до исполнения. TW-D04 можно разделить на оболочку и подключение; отсутствующий viewer блокирует только реальное подключение. Если релиз обещает настоящий Twin, одного fixture для релиза недостаточно.

До админки настройки интеграций хранятся в типизированной конфигурации/серверном окружении; потом управляются через интерфейс на том же контракте. На desktop не делать необратимых решений, мешающих reflow; мобильную вёрстку и её приёмку выполнять после desktop. При разработке уже выпущенного сайта новые функции проходят обе версии до публикации.

### W36.5. Шаблон задания ИИ-разработчику
> Выполни только пакет <ID> по его карточке. Master используй как стандарт, профиль — как границы проекта. Прочитай перечисленные входы и conventions репозитория. Сохрани принятые тексты/визуальный принцип. Реализуй указанный сценарий, состояния и mobile. Проверь критерии, исправь обнаруженное и обнови checkpoint. Не расширяй scope на соседние модули. Если зависимость отсутствует, укажи точный блокер; не объявляй mock реальной интеграцией. Следующий пакет запускай только в пределах порученного этапа.

### W36.6. Приёмка процесса
**PIPE-QA-01.** Для каждого integrated-пакета доступны карточка, версия результата и доказательства проверки. Нет пакетов «готово», подтверждённых только отчётом генератора.
**PIPE-QA-02.** Исполнитель после перезапуска может определить текущий результат и продолжить по checkpoint. Отсутствие Twin/CRM не маскируется локальной имитацией.

## W37. Интеграции, пользовательский код и внешние сервисы

### W37.1. Назначение
Решение владельца: предусмотреть подключение произвольных необходимых интеграций, включая вставку кода в head/тело/футер. Ниже — требования к реализации этой возможности. Это не утверждение, что конкретные сервисы уже подключены.

| Способ | Для чего | Место исполнения |
|---|---|---|
| Готовый коннектор | Счётчик, CRM, коллтрекинг, чат, сквозная аналитика | По контракту конкретного сервиса |
| Пользовательский HTML/JS | Разрешённый код виджета/сервиса | head, body_start, body_end |
| Визуальный слот | Контент/виджет именно внутри header, footer или блока страницы | Именованный slot компонента |
| API/webhook | Серверный обмен данными и событиями | Сервер/очередь, без клиентского секрета |

`head` — техническая часть HTML; header — видимая шапка. Футер страницы и код перед `</body>` также различаются. В интерфейсе эти варианты подписываются однозначно.

### W37.2. Реестр и редактор
**EXT-01.** Раздел «Интеграции» содержит название, тип, владельца, среду (dev/staging/production), область сайта/страниц, место вставки/слот, конфигурацию, режим загрузки, зависимости, включённость, версию и статус последней проверки.
**EXT-02.** Для пользовательского кода доступны поля head/body_start/body_end и подключаемые визуальные slots. Статусы draft → preview → enabled/disabled; история, сравнение изменений, возврат к версии. Проверку синтаксиса/схемы не выдавать за доказательство безопасности или полезности кода.
**EXT-03.** Права редактирования произвольного исполняемого кода отделены от редактора контента и обычной роли маркетолога. Разрешение выдаёт владелец/администратор по профилю. Просмотр/сохранение в админке не исполняет введённый код; preview запускается в отдельной среде/изоляции с предупреждением о фактической отправке событий внешнему сервису.
**EXT-04.** Область: весь сайт, разрешённые маршруты/шаблоны, исключения; внутреннюю админку исключать по умолчанию. Секреты/API-ключи серверных сервисов не допускаются в публичном snippet. Публичный ID счётчика и секрет — разные категории.
**EXT-05.** Предусмотреть отключение конкретной интеграции и общий аварийный режим без необязательных snippets. Сайт/форма работают при недоступности внешней аналитики. Выключение в конфигурации применяется новым загрузкам/маршрутам; для уже работающего стороннего скрипта определить cleanup/reload, не обещать мгновенно отменить отправленные данные.

### W37.3. Исполнение и данные
**EXT-06.** Загрузка учитывает требования сервиса, порядок зависимостей, async/defer и политику согласий проекта. CSP/nonces и разрешённые внешние домены настраиваются целенаправленно; не отключать защиту целиком ради одного скрипта. Конкретные параметры брать из документации поставщика при подключении.
**EXT-07.** При клиентской маршрутизации согласовать pageview и повторную инициализацию. Один сервис не устанавливается одновременно через коннектор, snippet и tag manager. Дедупликация проверяется по фактической отправке, включая Back/Forward и повторное открытие демо.
**EXT-08.** Единый словарь событий W22: проект/лот, демо, форма, результат принятия обращения; сквозная аналитика получает согласованные attribution/CRM связи. Не передавать содержимое личных документов, контакты или секреты в общедоступные события по умолчанию.
**EXT-09.** Серверные подключения имеют схему, авторизацию, проверку подлинности webhook, идемпотентность, retry, журнал и ограничение доступа. Статус «код сохранён», «скрипт загружен» и «событие принято сервисом» различается.
**EXT-10.** Для публикации/редактирования/версии настроек предусмотреть инвалидацию кеша и предсказуемое применение. Сторонний отказ не блокирует основной renderer. Произвольный код может нарушить страницу: предусмотреть возможность восстановить предыдущую конфигурацию без входа на сломанную публичную страницу.

### W37.4. Критерии приёмки
**EXT-QA-01.** Вставка в каждую зону выполнена в правильном месте и только на разрешённых страницах; отдельный header/footer slot не подменён head/body_end.
**EXT-QA-02.** Включение/выключение, версия/откат, права, окружения, повторная навигация, отказ внешнего сервиса и совместимость с политикой согласий проверены.
**EXT-QA-03.** Для аналитики показать фактическое тестовое событие в выбранном сервисе и отсутствие дубля; для CRM — подтверждение доставки. До доступа к сервису статус BLOCKED, не PASS.
**EXT-QA-04.** Проверить влияние на desktop/mobile, загрузку, форму и демо. До разработки админки поддерживается конфигурационный путь; сам UI редактора — отдельный пакет TW-A02.
