# Twin by TALENT — Frontend Implementation & Visual Translation Spec

Стартовый порядок и распределение ролей источников: `../START_HERE_TWIN.md`. Визуальная композиция — по концептам; UI-каталог задаёт содержание и поведение состояний.

Версия 1.2 · 18.10.2026 · статус: developer handoff, предложенная реализация актуального концепта. Реальный сайт, backend и motion этим документом не создаются.

## 1. Задача и исходники

Собрать адаптивную главную `/` Twin из семантических компонентов. Сайт продаёт девелоперу цифровую инфраструктуру продаж; изображённая недвижимость служит демонстрацией. Ядро — коммерческий цифровой двойник; операционный слой — виртуальный отдел продаж.

Основные визуальные опоры в `03_REFERENCES`: `TWIN_WEBSITE_PART_01.png`, `TWIN_WEBSITE_PART_02.png`, `TWIN_PRODUCT_COMPOSITION.png`, `TWIN_DELIVERY_TRIANGLE.png`. Первые две — последовательные части ОДНОЙ страницы. Их нельзя использовать как растянутые фоновые изображения вместо вёрстки. Отдельные композиционные эталоны важнее мелких искажений в сборочных растрах.

Содержательный источник: `TWIN_SOURCEBOOK_v1_2026-10-16.md`, разделы twin-master и twin-resort; последние решения владельца 17–18.10 имеют приоритет. В пакет включён снимок актуальной текстовой концепции. Приложенные спецификации ПИН от 21.09 использованы только как метод организации разработки: статичная истина → компоненты → состояния → motion → QA. Палитра, кристаллы, инвестиционный маршрут, тексты и SEO ПИН не наследуются.

Приоритет: последнее решение владельца → этот handoff и motion spec → содержательные источники Twin → визуальные опоры → conventions репозитория. Старые отменённые слоганы и прежнее позиционирование не восстанавливать из источника.

## 2. Scope и существенные статусы

Актуальный объём и этапы — `TWIN_SITE_IMPLEMENTATION_PROFILE.md` P02. Этап A сохраняет главную v1.1, добавляет маршрут `/demo`, оболочку подключения и резервный выбор. Этап B подключает предоставленный настоящий Twin. Backend-обращения — C; CMS, ИИ и рабочее управление — D. Реальные брони, платежи, переоценка и создание нового 3D-двойника не входят в A/B. Готовность каждого этапа проверяется отдельно.

| Положение | Статус для разработки |
|---|---|
| Белая основа, сквозная архитектурная сцена | Принятая рабочая концепция |
| G | Выбран для примерки сайта; точный отдельный production-master не предоставлен |
| Карта состава с ядром и шестью компонентами | Одобренная визуальная рабочая основа; не юридическая комплектация каждого договора |
| 3 месяца | Данные владельца для блока реализации; начало отсчёта и границы поставки уточняются в предложении |
| В среднем 5 млн ₽ | Данные владельца; среднее, не «от» и не фиксированная цена каждого проекта |
| Превосходство над всем рынком | Не доказано; не публиковать «самый быстрый/дешёвый» |
| Демопроект, изображения, показанный UI | Иллюстрации; не кейс внедрения и не реальные коммерческие данные |
| Наличие конкретных интеграций и расширений | По согласованной конфигурации |

До публичного выпуска проверить стоимость, срок, права на медиа, лицензию шрифта, политику персональных данных и точный логотип. Это конкретные выпускные зависимости, не повод откладывать локальную реализацию.

## 3. Пространственная партитура

Панорама проекта → выбранный фасад как вертикальная опора → пространство и лот → рабочий интерфейс → изометрическая карта продукта → каналы применения → условия реализации → обращение.

Сохраняемый предмет — проект и выбранный лот, а не декоративная линия. У архитектурного кадра меняется масштаб и роль. Вся страница светлая; тёмная аналитическая среда ПИН сюда не переносится. Разные типы эпизодов обязательны: открытый hero, протяжённый фасад, точный UI, изометрическая карта, широкая офисная сцена, компактная геометрическая аргументация, спокойная форма.

Иллюстративные кадры из пакета принадлежат одной художественной семье, но не доказанной BIM-модели. Перед непрерывным morph/camera move требуется сверить геометрию или получить согласованные исходники; без этого использовать монтажные маски/срезы и crossfade.

## 4. Контент и компоненты страницы

### S01 — Header / Hero

Меню: Продукт → `#product`; Сценарии → `#channels`; Состав и запуск → `#composition` с дополнительным якорем `#delivery`. Primary: «Посмотреть Twin» открывает `/demo`; `#product` остаётся кратким обзором; secondary: «Обсудить проект» → `#contact`.

H1: **Цифровая инфраструктура продаж девелоперского проекта.**

Текст: «Раскрывайте преимущества проекта и помогайте покупателю выбирать — на сайте, дистанционно, через агентов и в офисе продаж.»

Панорама справа, текст на чистом белом поле слева. Подпись «Демонстрационный проект» живым текстом. Полный G со спокойным охранным полем. Desktop rail: Проект / Пространство / Лот / Система; это глобальные якоря, не второй селектор корпуса. Mobile — обычное компактное меню, без вертикального текста.

### S02 — AdvantagesJourney

H2: **Покажите, что делает проект ценным.**

Текст: «Окружение, архитектура, инфраструктура, планировка и вид — в связи с конкретным выбором покупателя.»

Три смысловых состояния одного эпизода:

| ID | Маркер | Материал и единственная выноска |
|---|---|---|
| project | Проект | Общий контекст / фасад: Окружение и архитектура |
| space | Пространство | Терраса / интерьер: Территория и пространство |
| lot | Лот | Выбранная часть и план: Планировка, положение и вид |

На desktop высокий фасад связывает материалы справа; текст не накладывается на пёстрые детали. На mobile материалы идут последовательно. Смысловые этапы доступны без JS и без скролл-анимации.

### S03 — ProductDemo (`#product`)

H2: **Исследуйте проект. Рассмотрите конкретный лот.**

Демонстрационный UI: breadcrumb Проект / Корпус / Этаж / Лот, выбор корпуса и этажа, выбор доступного демолота, вкладки Планировка / Вид, возврат к предыдущему уровню. Контролы — DOM, не запечённый скрин. Центральный обзор ведёт на `/demo`; настоящий viewer подключается через `TWIN_INTEGRATION_CONTRACT.md`. Не выдавать демо за подключённый Twin.

State: `projectId`, `buildingId`, `floorId`, `lotId`, `view`. Выбор нового корпуса сбрасывает несовместимые этаж/лот; выбор этажа сохраняет лот только если он принадлежит этажу. «Вернуться к проекту» сбрасывает глубину, не перезагружает страницу. Не рисовать кликабельные этажи, если для них нет demo records. Начальный fixture: один корпус, один этаж, один лот, два медиасостояния; расширять только согласованным набором. Подпись «Демонстрационный интерфейс». Цены, доходность и статусы продаж не выдумывать.

### S04 — ProductComposition (`#composition`)

H2: **Из чего состоит Twin**

Текст: «Коммерческий цифровой двойник и связанные компоненты системы продаж».

Центр: изометрический проект, маркер «Ядро продукта», подпись «Коммерческий цифровой двойник». Вокруг шесть навигационных компонентов:

| ID | Название | Подпись |
|---|---|---|
| client-tools | Клиентские инструменты | Исследование, подбор и персонализация |
| virtual-sales | Виртуальный отдел продаж | Рабочая среда команды и агентов |
| content-system | Контентная система | Материалы на общей цифровой основе |
| management | Управление и аналитика | Данные проекта, ассортимент и спрос |
| integrations | Интеграции | Связь с CRM и системами девелопера |
| commercial | Коммерческие модули | Ремонт, мебель и связанные сервисы |

У последнего — метка «Расширение». Подпись карты: «Конфигурация собирается под задачи проекта». Не заменять компоненты функциями вроде вида из окна или генплана. Каналы применения находятся в следующем блоке.

Изображения и подписи — отдельные слои, порядок чтения задан DOM. SVG-связи декоративные, `aria-hidden`; номера и пиксельные координаты не должны быть единственным способом навигации. Desktop — центральное ядро и 3+3 компонента; tablet — центральный макет и две колонки; mobile — один макет и читаемый список кнопок. Кликабельны и предмет, и подпись; связь не пересекает название.

#### Модалки и будущие страницы

Открытие по нажатию/Enter, hover только дополняет focus. Модалка: H2, одно предложение о назначении, основной медиаматериал, состав, связь с ядром, условия подключения и CTA «Обсудить конфигурацию». Контентный объём соответствует компоненту. Не показывать одну функцию как полное описание отдела продаж.

| Компонент | Содержание внутри модалки |
|---|---|
| client-tools | Поиск/подбор, карточка лота, сравнение/сохранение, пространственное исследование, персонализация |
| virtual-sales | Рабочее место, контекст клиента, подборки, предложения, обращения; коммерческие шаги — по комплектации |
| content-system | Рендеры, планы, изометрии, панорамы, видео и карточки как материалы одной цифровой основы |
| management | Источники данных, ассортимент/статусы, обновление, аналитика поведения; без обещания автоматического ценообразования |
| integrations | CRM и источники ассортимента: состав полей, направление обмена, поддерживаемая конфигурация; не рисовать действующие логотипы интеграций без проверки |
| commercial | Отделка, мебель, комплектация, подрядчики и сервисы как расширения |
| core | Территория, здания, пространства, этажи и лоты; связь цифровой модели с остальными компонентами |

Тексты раскрытия — проектный scope, описанный в sourcebook; production-наличие каждой функции подтверждается отдельно. Внешнюю модалку не перегружать внутренними статусами проверки: показывать понятный состав и условия конфигурации.

URL-контракт первого прохода: `?component=client-tools#composition`; другие IDs аналогично, ядро `core`. Ссылка без JS должна вести к доступному разделу/резервному описанию. Открытие добавляет запись history; закрытие возвращает исходный URL, back закрывает диалог. При прямом URL close через replace удаляет параметр. Focus trap, Escape, возврат фокуса к инициатору, блокировка прокрутки с компенсацией scrollbar, `aria-modal`, inert background. CTA закрывает диалог, прокручивает форму и добавляет тему обращения. При будущем переходе на `/product/<slug>` сохраняется content ID, меняется route resolver; до создания страниц не вести на 404.

### S05 — SalesChannels (`#channels`)

H2: **Один цифровой проект. Вся система продаж.**

Подпись: «Единая цифровая основа для всех каналов продаж».

Четыре tabs: Сайт / Онлайн-показ / Агент / Офис продаж. Начальный desktop кадр — Офис продаж. Сайт: самостоятельное изучение и обращение; Онлайн-показ: совместный просмотр выбранного лота; Агент: показ и подборка на встрече/дистанционно; Офис: большой экран и предметное обсуждение. Медиа для каждого различается, проект и выбранный лот общие. В пакете есть четыре разные иллюстрации каналов: офисный фон в02_BACKGROUNDS, сайт/онлайн/агент в08_CHANNEL_MEDIA. Это постановочные demo-изображения, не скриншоты фактического внедрения. Состояния доступны в06_UI_KIT, PNG в07_UI_STATES. Tabs управляются с клавиатуры; нет автоматического переключения. Ошибка загрузки медиа не скрывает текст и CTA.

### S06 — Delivery (`#delivery`)

H2: **Быстро. Доступно. Качественно.**

«В Twin сходятся все три.» / «Обычно предлагают выбрать два.»

Три опоры: Быстро — **3 месяца**, Разработка и сдача проекта; Доступно — **В среднем 5 млн ₽**, Конфигурация под задачи проекта; Качественно — **Посмотрите в работе**, Архитектура. Интерфейс. Сценарий выбора. Действие — «Посмотреть Twin».

Треугольник — коммуникационная метафора, не измеренная диаграмма рынка. Рёбра SVG, подписи DOM, модель небольшая. Среднюю стоимость не превращать в минимальную. Числа не анимировать от нуля. Никаких логотипов конкурентов и абсолютного превосходства.

Четыре этапа: Материалы и задачи → Состав решения → Разработка → Проверка и запуск. Объяснения: изучаем проект и цели; предлагаем конфигурацию и фиксируем параметры; создаём и наполняем двойник; тестируем и запускаем. Не приписывать этапам произвольные месяцы. Примечание: «Состав решения, стоимость и график фиксируем для конкретного проекта».

### S07 — Contact (`#contact`) / Footer

H2: **Посмотрите, как Twin может работать на вашем проекте.**

«Обсудим задачи и подготовим конфигурацию решения.» Поля: Имя (required), Компания (required), Телефон или email (required), Ссылка на проект (optional). Добавить невидимую пользователю техническую защиту от spam только по backend-контракту; не собирать лишние данные. Checkbox согласия не предзаполнен, со ссылкой на реальную политику перед выпуском.

Состояния: idle → validating → submitting → success/error. Отправка в реальный endpoint — только после подключения. В локальном prototype submit показывает «Демонстрационная форма: данные не отправлены», не ложное «Заявка отправлена». При ошибке сохранить поля и дать повтор; double-submit заблокировать; ошибки связаны с полями через `aria-describedby`, результат через live region. Тема компонента из модалки видна и редактируема. Футер: G и меню; реальные контакты/юрданные подключаются владельцем, не придумываются.

## 5. Архитектура реализации

До кода: определить framework, routing, styling, package manager, зависимости и pipeline. Сохранить существующий stack. Для greenfield предложен React + TypeScript с серверной/статической выдачей текста, без фиксации версий пакетов в этом ТЗ. Потребность в Next.js определяется инфраструктурой, не анимацией.

Компоненты: `Header`, `Hero`, `AdvantagesJourney`, `ProductDemo`, `ProductComposition`, `ComponentDialog`, `SalesChannels`, `DeliveryTriangle`, `LaunchSteps`, `ContactForm`, `Footer`; shared `ResponsiveMedia`, `Reveal`, `useReducedMotion`, `useScrollScene`. Content/data отдельно от JSX и motion. См. `04_DATA/twin-home-content.json`.

Карта продукта хранит ID, название, описание, media, modal sections, optional route. Медиамодель: `id`, `src`, `alt`, `width`, `height`, `focalPoint`, `poster`, `kind`, `status`. Состояния `idle/loading/ready/error` обязательны для тяжёлых материалов. React key по ID, не индексу.

Картинки `02_BACKGROUNDS` — оригинальные AI-ассеты, не рабочий 3D, не модели и не слоёные исходники. Крупные UI-фрагменты из растра не превращать в фиктивные controls. G в05_LOGOS предоставлен отдельным рабочим растровым PNG. Это AI-реконструкция принятого варианта по листу G–L, не утверждённый точный векторный мастер. Проверить геометрию перед финализацией айдентики. В пакет сохранён сравнительный лист G–L, нужная ячейка G — верхняя левая.

## 6. Визуальные правила и адаптация

Белая тёплая база, графит, дозированная бронза, контрастные подписи действий. Точные production-токены и гарнитуры остаются предметом настройки Twin; не объявлять токены ПИН каноном. Предлагаемый старт: paper `#FAFAF8`, ink `#232526`, muted `#60666B`, bronze-deep `#8B6138`, border `#DFE1DD`. Проверить фактический контраст; цвет концептуального растра не измеренный эталон. Заголовки — геометрический sans, body/UI — нейтральный кириллический sans с проверенной лицензией.

Desktop ≥1280: max-width 1320–1440,12 колонок, внешнее поле от32px; tablet 768–1279: 8 колонок/упрощённый rail; mobile <768: 1 колонка, поля20px (16px на320), H1 clamp32–56px, body16–18px. Это исходные параметры реализации, не окончательный token master. Проверять320/390/768/1024/1440/1920px. Кнопки минимум44×44px; карта и треугольник превращаются в последовательные смысловые элементы. Изображения кадрируются отдельно для mobile, текст не сохранять только внутри изображения. У hero отдельное mobile изображение/кроп, запрет на уменьшение desktop целиком.

## 7. SEO, доступность, performance

Один H1, H2 по блокам, indexable DOM, alt по назначению, decorative layers aria-hidden. Title/description Twin согласовать отдельно, SEO-кластеры ПИН не применять. JSON-LD только по реально предоставленным данным. Ссылки на страницы появляются после создания страниц.

Keyboard, visible focus, dialog/tab semantics, контраст WCAG AA, отсутствие focus trap вне диалога. Тексты видны при отключении JS и reduced motion; не прятать SEO-copy opacity0 до загрузки JS. Нативный scroll, без автоперелистывания и scroll-jacking.

Плановые бюджеты: LCP≤2.5s, INP≤200ms, CLS≤0.1 при полевых p75; локальный lab не доказывает field. Hero — responsive AVIF/WebP с eager/high priority только для реального LCP. Ниже fold — lazy с размерами и placeholder. Alpha-слои из PNG оптимизировать с проверкой краёв. Начальная передача: ориентир≤1.5MB, hero≤500KB; декодированные4K PNG не грузить все сразу. Значения — цели, не измеренные результаты. Без серверного репозитория build и Lighthouse не запускались.

## 8. Порядок разработки и приёмка

1. Audit repository и assets; составить dependency map и выделить недостающие production-ассеты.
2. Static truth всех7 эпизодов + responsive. Сверить с обеими частями, без advanced motion.
3. Product demo, composition dialogs, channel tabs, honest contact adapter.
4. Motion отдельными сценами по парному документу; сначала фасад, затем карта, затем треугольник.
5. Build/lint/typecheck по repo. E2E ключевых сценариев, keyboard, прямые URL диалогов, browser back/forward, submit failure/success с test endpoint.
6. Visual QA на6 ширинах; реальные screenshots; проверить стыки фасада, масштаб карты, текст и alpha edges.
7. Performance, Safari/iOS, reduced-motion и JS-disabled fallback; затем готовить выпуск.
