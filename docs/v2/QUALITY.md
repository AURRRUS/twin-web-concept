# Twin V2 — контроль результата и расхода
27.10.2026. Применяется к исправлениям и продолжению V2. Владелец уже разрешил выпуск без согласования снимков; этот порядок не добавляет approval gate владельцу.

## Три независимых результата
technical: сборка/поведение; visual: соответствие выбранному референсу и последним решениям; owner: оценка владельца. Не называть technical PASS выполнением визуального задания. Снимок не доказывает рабочую анимацию, реальные шрифты не доказывают удачную типографику.

## До кода
Прочитать только V2_START, текущую задачу и затронутые файлы. Зафиксировать объём страницы явно: весь сайт или названные разделы. Не дробить обещанный весь сайт на два экрана без решения владельца. Взять последние решения выше растра. Разложить ключевой визуальный приём на реальные ассеты/DOM/SVG; назвать недостающий материал ДО реализации. Не использовать оговорку «production plausible» для молчаливой замены архитектурной сцены обычной диагональю.

## Рабочий цикл
1. Сначала собрать полноценный неподвижный фрагмент с реальными шрифтами/ассетами и контекстом соседних блоков.
2. Сопоставить reference и browser кадр в одинаковом размере. Назвать наблюдаемые расхождения: размеры/переносы, геометрия, медиа и роль движения. «Выглядит премиально» не наблюдение.
3. Исправить конкретные причины. Не запускать повторно весь ресёрч, генерацию картинок, все скиллы и матрицу размеров ради изменения одного отступа.
4. После исправления статичной композиции добавить движение. Проверить начало/середину/конец, обратный ход, повторный вход, управление и mobile.
5. Один полный прогон матрицы на кандидате выпуска; повторять затронутую часть при правках. После двух неудачных визуальных итераций сменить способ реализации/разобрать причину; не повторять тот же промпт и весь дорогой прогон.
6. Исполнитель заполняет .twin/v2/visual-review.json по фактическим наблюдениям, не авансом. Скриншоты делает и оценивает исполнитель, владельцу не нужно подтверждать их. На каждую проверку — конкретный reference, изображение браузера, observed и remaining. Допустимы инженерные отличия только если не нарушают решение владельца и описаны с причиной. Критические расхождения нельзя объявить исключением.
7. npm run quality:v2 проверяет актуальность review относительно всех runtime inputs и наличие реальных PNG/JPEG evidence. При FAIL publisher блокируется до исправления; текущая опубликованная версия остаётся доступна. Автомат не оценивает вкус и не подтверждает честность самооценки: художественное суждение — ответственность исполнителя.

## Время и ресурсы
Не обещать заданный процент лимита: расход модели инструментально этим репозиторием не ограничивается. Тратить на задачу: адресное чтение → изменение → локальная проверка → финальный прогон. Не создавать новый workflow/архив на каждую правку. Сводить запросы чтения; не печатать в чат весь diff/дерево/бинарники. Если зависание среды/повторные сборки съедают время, сообщить конкретный блокер и сохранить работу; не подменять прогресс количеством тестов.

## Evidence contract
Критерии обязательны: hero, transition, journey, mobile, motion. В каждом объекте: id, status:pass, referencePath, referenceSha256, evidence[{path,sha256}], observed (конкретно, не менее40знаков), remaining:[] . Минимум один browser evidence на критерий; motion — минимум3кадра. Можно переиспользовать один кадр для связанных критериев. Файлы держать docs/v2/reviews/ или artifacts/v2-review/, включать нужные в Git для CI. До переноса картинки проверить, что это browser screenshot, а не референс. referencePaths задаёт requirements.json.
Обновление inputs: node scripts/visual-gate-v2.mjs --fingerprint. В review записать полученный SHA после последнего изменения runtime, затем проверить gate. Любое изменение исходников V2/общих lib/fonts/media, токенов, контента и build скрипта делает старый review неактуальным. Изменения только текста отчёта не требуют новой браузерной матрицы.
