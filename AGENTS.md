# Twin by TALENT — рабочие инструкции

## Вход и границы
Прочитать `TWIN_START.md` → `.twin/START.md` → `.twin/state.json`. Единственный реестр изменяемых указателей — `.twin/state.json`: текущая workflow-задача, site candidate, рабочая ветка, source baseline, отдельные V1/V2 и ранее опубликованная версия. Файлы `.twin/project.json` и `.twin/v2/project.json` — ссылки на реестр, не второй источник состояния. Исторический `main` не является автоматическим указанием текущей рабочей ветки.
Сверить фактические remote/branch/HEAD и незакоммиченные изменения. Сохранить более свежую работу; не делать reset/force-push и не переносить V2 поверх V1. `sourceCommit` candidate описывает проверенную исходную версию runtime, а не обязуется совпадать с каждым новым коммитом документации.
Последняя явная инструкция владельца выше старого документа. Режим и scope читать из активной задачи; сам факт наличия site candidate не разрешает её исполнять при инфраструктурной задаче. Решения сохранять в `.twin/DECISIONS.md`, для V2 также `docs/v2/DECISIONS.md`.

## Команда
Web Production (`.agents/skills/web-production/SKILL.md`) — главный координатор сквозной работы. Frontend Engineer (`.agents/skills/frontend-engineer/SKILL.md`) — инженерный соавтор/исполнитель. Twin Site — адаптер источников, бренда, маршрутов и выпуска Twin. Маршрутизация специалистов — `.twin/ROUTING.md`; читать реальные SKILL и PROJECT_OVERRIDE.
Для существенной работы с конвейером реально запустить отдельного исполнителя и затем независимого reviewer. Записать фактические ID, scope, входную версию, результат и evidence. Автор не принимает свою работу как независимый reviewer. Если функции среды нет, отметить ограничение и сохранить handoff; названия ролей и чтение навыков не являются запуском агентов. Для мелкой правки не разворачивать всю команду.

## Реализация
Любую новую задачу оформить по `.twin/TASK_TEMPLATE.md`, проверить `node scripts/twin-system.mjs task <id>`. Порядок: контекст → измеримый контракт → контрольный образец при новом графическом производстве → статика → адаптив → motion → проверка/исправления → разрешённый выпуск → RESULT/HANDOFF. Не запускать серию графики до принятой пробной сцены.
Для V2 читать `V2_START.md`, канон типографики по `profiles.v2.typographySource`, наследуемое `.twin/tasks/VIS-004/ENGINEERING.md` и действующий контракт candidate. ENGINEERING наследуется в типографике и бренде; отменённые задания на иной hero, переделку всей страницы и публикацию не расширяют текущий scope. При конфликте desired и observed не менять критерии ради PASS и не менять CSS без задачи.
Для V1 сохраняются `.twin/tokens.json` и `.twin/assets.json`; не применять V1 числа к V2 автоматически. Не переносить бренд ПИН в Talent. Не ставить точки в конце заголовков; короткие предлоги/союзы связывать со следующим словом без склеивания длинных фраз. Защищать архитектуру, пропорции и составляющие реального объекта.
Для визуальной реализации FE читает reference-to-code.md, visual-task.md и visual-review.md; для слоёв — asset-production.md, prompt-mask-effects.md и parallax.md. Картинка целой страницы не заменяет редактируемый интерфейс. Motion задаётся числами и состояниями, с обычной прокруткой, выходом, reverse, keyboard/mobile/reduced-motion.

## Проверки и публикация
Technical PASS, визуальный вердикт, одобрение владельца и deployment — разные состояния. Проверять действующие route/controller, не приписывать тестам старого helper приёмку новой сцены. Review привязан к runtime inputs, контракту, reference и состояниям; старые отчёты сохраняют историческую область действия.
Для V2 читать `docs/v2/QUALITY.md` и актуальное разрешение из `publicationAuthority.source` в реестре. Сохранённое разрешение рабочего preview с известным дефектом не является visual PASS или финальной приёмкой. Инфраструктурная задача не публикует сайт. Для разрешённого V2 выпуска использовать только `publish:v2`, сохранить V1 и проверить фактическую онлайн-версию после deploy.
Не вводить повторное согласование снимков к уже разрешённому выпуску. Принятые владельцем контрольные точки фундамента, ключевых сцен, пробного графического материала и финала соблюдать. При недоступном инструменте писать NOT RUN и точное ограничение. Завершать реальным результатом и следующим шагом, не только планом.
