# Порядок работы и восстановление контекста

## 1. Найти одну текущую версию
Прочитать `AGENTS.md` и `.twin/state.json`. Единственный реестр содержит `workingBranch`, `workflowTask`, `siteCandidate`, `profiles` и ссылку `publicationAuthority`. `.twin/project.json` и `.twin/v2/project.json` — совместимые входные ссылки с `statePath` и `profile`; их нельзя читать как прежние независимые реестры.
Сверить фактические remote heads, текущую ветку/HEAD и `git status`. Реестр фиксирует основание, не разрешает откатывать более свежую работу. `siteCandidate.sourceCommit` — исходный runtime baseline; документационные коммиты могут быть новее без новой браузерной приёмки. Записанный опубликованный source — отдельная версия; пометка registry-only не означает проверку live.
При работе без clone использовать доступный GitHub connector. Начинать с ветки, указанной в текущем задании владельца; не выбирать старую ветку только потому, что она называется main или содержит historical canonicalBranch.

## 2. Восстановить предмет и границы
Прочитать в таком порядке:
1. TASK.md и task.json по `workflowTask.path`, затем его последний RESULT.md/HANDOFF.md, если существуют.
2. `.twin/DECISIONS.md`, `.twin/ROUTING.md`; для V2 — `docs/v2/DECISIONS.md` и `V2_START.md`.
3. TASK.md, task.json, visual-contract.json, asset-jobs.json, run.json и REVIEW.md по `siteCandidate.path`, если работа затрагивает candidate или инфраструктуру его проверки.
4. Исходники из sources задачи, профильные каноны и фактический затронутый код. Для V2 типографику читать по `profiles.v2.typographySource` и наследовать ENGINEERING из VIS-004 в действующей области.
5. Открытые дефекты candidate из реестра, соответствующие evidence и последнее решение о выпуске по `publicationAuthority.source`.
Не превращать отсутствующий RESULT в выполненную задачу, старый review — в свежую приёмку, а рабочий preview — в одобрение владельца. Если workflow-задача завершена, продолжение берётся из её HANDOFF и последней команды; следующая визуальная работа не начинается автоматически.

## 3. Выбрать режим и оформить контракт
`prepare` — подготовка, `review` — проверка без реализации, `execute` — сделать/исправить/внедрить. Последняя явная инструкция определяет режим в пределах задачи. Наличие задачи или артефакта не запускает исполнение само по себе.
Из обычной правки команда сама заполняет TASK_TEMPLATE и task.json: результат, scope, тексты/сущности, числовая типографика, изображения, responsive, motion, проверки и выпуск. Владелец принимает продуктовые и визуальные решения, а не вычисляет маски или CSS. Для нового инженерного значения записать источник и статус, не приписывать владельцу одобрение.
Проверить контракт `node scripts/twin-system.mjs task <id>`. Промпт и исходники должны быть реальными файлами в Git; история чата не является единственной памятью.

## 4. Выполнить с реальной командой
Web Production ведёт зависимости и результат; Frontend Engineer составляет измеримый контракт, заказы на графику и реализацию; Twin Site хранит только особенности Twin. Минимальный состав специалистов — по ROUTING.
Для существенного workflow реально делегировать исполнение и отдельную проверку. Записать ID, scope, входную версию, выход и evidence. При недоступной функции среды назвать её и оставить обязательство открытым. Не переименовывать self-review в независимый.
Новая графика: сначала контрольная сложная сцена, затем согласованный набор. Реализация: статика → адаптив → motion. Не переписывать смысл и соседние блоки ради удобства вёрстки. Защищать архитектуру реального объекта; сильную альтернативу сначала показать рядом и получить выбор.

## 5. Проверить актуальный результат
Проверять затронутые механизмы и действующий route/controller. Браузерный проход визуальной задачи включает обычный scroll до footer, выход, reverse/re-entry, resize, mobile/keyboard/reduced-motion и controls. Screenshot и computed styles не доказывают плавность или художественное качество.
Review должен соответствовать runtime inputs, контракту и reference. При дефекте воспроизвести → исправить причину → повторить затронутую проверку; не менять критерий ради PASS. Недоступное обозначить NOT RUN. Исторические результаты сохранять с их фактической областью.

## 6. Выпустить по разрешению и сохранить память
У разрешения визуального candidate один источник, указанный `publicationAuthority.source`. Scope текущей workflow-задачи проверяется отдельно: её запрет публикации не отменяет ранее данное разрешение candidate, но не позволяет выполнить его как побочный эффект. Для final требуется одобрение владельца; working preview может иметь явно принятые для просмотра дефекты без visual PASS.
При разрешённом V2 выпуске сохранить V1, выполнить gate и проверить live source/маршрут после deploy. Не вводить повторное согласование снимков к уже разрешённому выпуску.
Сохранить RESULT/HANDOFF: фактические изменения и команды, версия, review, ограничения, что принято/не принято и следующий конкретный шаг. Обновлять указатели только в `.twin/state.json`, не дублировать их в стартовых Markdown. Если сайт не публиковался, прямо назвать это.
