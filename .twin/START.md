# Порядок работы
## 1. Установить контекст
Прочитать project.json, DECISIONS.md, DESIGN.md и затронутую задачу. Получить фактические remote heads и опубликованный sourceCommit; baseline в файле — исторический снимок, не разрешение отката. Проверить git status. Сохранить чужие изменения; изолировать свою ветку от актуальной канонической ветки. Если свежая версия найдена в другой ветке, сначала сопоставить её изменения, обновить указатель только после проверки, не переключаться вслепую.
Если локальных файлов нет, открыть через подключённый GitHub `main/TWIN_START.md` и `main/.twin/project.json`, затем получить canonicalBranch. Использовать API/connector или fetch/clone; не считать отсутствие локальной копии отсутствием GitHub.
## 2. Выбрать режим
`prepare`: просьба подготовить ТЗ, обсудить или просто назвать проект. `review`: просьба проверить без реализации. `execute`: сделать/исправить/внедрить/выполнить. Последняя явная инструкция определяет режим. Подготовленную JRN-001 не выполнять автоматически при просьбе собрать систему.
## 3. Собрать контракт
Из обычной правки исполнитель САМ заполняет TASK_TEMPLATE и task.json: ожидаемый результат, границы, точные тексты, роли оформления, изображения, responsive, взаимодействия, motion, проверки и условия публикации. Не требовать от владельца CSS-параметры. Существующая роль используется целиком. Для отсутствующей роли предложить и записать инженерное значение с происхождением; не называть его утверждённым владельцем. Только конфликт продуктового решения требует уточнения.
Прочитать навыки по ROUTING.md. Создать задачу `npm run twin:task -- new ID`; заполнить; проверить `npm run twin:task -- ID`; получить полный промпт `npm run twin:task -- prompt ID`. Показать промпт текстом, сохранить файлы и commit. Не оставлять TODO в ready-задаче.
## 4. Выполнить
Сначала неподвижная композиция с настоящими текстами и ассетами. Затем адаптив, только затем motion. Не переписывать смысл и соседние блоки под удобство вёрстки. Новое оформление ограничивать компонентом; глобальная миграция требует явного scope. DESIGN.md и tokens.json — одна система, не копировать значения по несвязанным селекторам.
Движение проектировать как состояния, вход/выход, паузы, reverse, повторный вход, быстрый ввод, resize и reduced-motion. Один прогресс управляет связанными элементами. Не связывать анимацию с количеством wheel-событий. При нехватке высоты выключать pin и сохранять читаемый поток, а не уменьшать текст до микрокегля.
## 5. Проверить и исправить
Выполнить ACCEPTANCE.md. Для каждого наблюдаемого дефекта: воспроизведение → конкретная причина → исправление → повторная проверка. Не менять тест на PASS вместо исправления. Если инструмент недоступен, указать NOT RUN и ограничение; не имитировать визуальную проверку числами. Соблюдать доступный браузерный навык.
## 6. Выпустить и запомнить
Если публикация разрешена текущей инструкцией, обновить publication.allowed в задаче с основанием, сделать резерв исходников и Pages, опубликовать после проверок без промежуточного согласования снимков. Сверить live sourceCommit и затронутый сценарий. В RESULT.md записать реальный commit, проверки, ограничения и URL, затем обновить память и канонический указатель при необходимости. Если публикация не разрешена, сохранить готовый результат в Git без выпуска.
Навык определяет процедуру, а не даёт техническую гарантию эстетики. Контракт, CI и браузер решают разные части задачи.
