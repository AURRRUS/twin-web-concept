# Как теперь разрабатывать сайты с GPT и Codex

Руководство владельца · Twin / Talent и ПИН · 1 ноября 2026 года

## Что мы получили

Подготовлены и проверены правила совместной работы команды: как восстановить задачу, разобрать визуал, передать работу разработчику, проверить результат и выпустить сайт. Для Twin исправлены противоречия в инструкциях, реестрах и проверках. Общую методику можно использовать в ПИН, но его бренд, код и продуктовые решения остаются отдельными.

Это ещё не завершённая «фабрика сайтов». Сейчас готов её рабочий порядок и проверки. Следующее доказательство — провести один сложный фрагмент Twin от исходного рендера до проверенной страницы, затем отдельный мобильный пакет ПИН.

|---|---|---|

| GPT + Web Production | Собирает задачу, ведёт смысл и конверсию, распределяет работу, сохраняет решения, возвращает дефекты исполнителям | Понятный пакет для реализации и фактический отчёт |
| Frontend Engineer | Измеряет композицию, задаёт типографику, слои, адаптив и движение, заказывает недостающую графику, реализует страницу | Код, материалы и доказательства проверок |
| Визуальные навыки | Готовят композиционные варианты и конкретные части изображения; усиливают качество по задаче | Проверяемый набор файлов с сохранённым исходником и лучшей версией |
| Codex | Восстанавливает контекст из репозитория, запускает доступных исполнителей, пишет код и тесты, сохраняет результат | Рабочая ветка с изменениями и отчётом |
| Независимый проверяющий | Проверяет фактическую реализацию по контракту и референсу | Вердикт, конкретные дефекты и подтверждения |

Навык — это инструкция. Агент — реально запущенный исполнитель. Прочитать три навыка не означает запустить три независимых агента. В текущей работе отдельные исполнители и проверяющие действительно запускались в GPT Work; поддержка таких запусков в конкретном внешнем клиенте Codex проверяется при начале работы.

## Как выглядит одна задача

1. **Ты описываешь результат обычным языком.** Например: «Доведи стык первого и второго экранов: сохрани исходный отель, сделай точный край здания, проверь мобильную версию». CSS, размеры маски и имена файлов заказывать вручную не нужно.
2. **GPT восстанавливает контекст и готовит пакет.** Команда сама находит текущую версию, принятые решения, нужный рендер, границы работ и критерии проверки. Не начинает новый дизайн из-за потери памяти.
3. **Frontend разбирает сцену.** Определяет сетку, размеры, шрифты, интервалы, crop, слои, маски, desktop/mobile и состояния. Значения из реального файла отделяются от приблизительных измерений по картинке.
4. **Команда показывает ключевой образец.** Если меняется визуальное направление или нужна серия новой графики, сначала показывается один сложный образец в контексте страницы. После его принятия команда производит остальные части самостоятельно.
5. **Codex реализует ограниченный пакет.** Сначала неподвижная композиция, затем адаптив, затем анимация. Если недостаёт материала, оформляется конкретный заказ, а не скрытая замена художественного приёма.
6. **Команда проверяет и исправляет.** Тесты проверяют поведение; отдельный reviewer — соответствие визуалу. Неудачная проверка возвращает работу исполнителю. Тебе не передают техническую ошибку как вопрос о вкусе.
7. **Ты принимаешь результат после команды.** Получаешь страницу или рабочий preview, короткий отчёт и оставшиеся отличия. Публикация выполняется по действующему разрешению проекта.

## Когда нужно твоё решение

Ты утверждаешь фундамент: цель и путь к действию, основные сущности страницы, типографику и визуальное направление. Затем — ключевой welcome, конверсионные экраны, самый сложный переход и представительный образец новой графики перед серией. Финальная приёмка остаётся у тебя после проверки команды.

Ранее принятое не спрашивается заново без изменения предмета. Команда самостоятельно считает размеры, исправляет ссылки, согласует реестры, строит маски, экспортирует файлы и устраняет ошибки кода.

Если команда видит вариант сильнее выбранного, она показывает оба в сопоставимом виде, объясняет выигрыш и последствия. Самовольной замены утверждённого направления нет.

## Как обращаться с рендерами и движением

**Точность объекта защищена отдельно от вёрстки.** Геометрия здания, этажи, окна, балконы, планы и реальные составляющие не меняются ради красивого кадра. На мобильном можно иначе расположить содержание и кадрировать сцену в согласованных пределах.

Большая картинка не считается готовым набором слоёв. Команда определяет, где нужны фон, архитектурный передний план, прозрачность, тень, SVG-геометрия и обычные элементы интерфейса. Слои собираются и проверяются в общем масштабе, а не только по отдельности.

Несколько прогонов улучшения — средство устранить видимый дефект, а не гарантия качества. У каждого прохода есть цель и предел; исходник и лучший результат сохраняются. Тридцать изображений без принятого образца не производятся.

Анимация получает понятный сценарий: вход, раскрытие, удержание, переход и выход. Команда задаёт длину прокрутки или время, поведение назад, при изменении окна и при отключённой анимации. Эффекты поддерживают смысл и решение пользователя. Для Twin нужны несколько сильных эпизодов; возможности длинного визуального путешествия пригодятся другим проектам, но не добавляются автоматически.

| Проект | Приоритет при компромиссе |
|---|---|
| ПИН | Качественная мобильная версия и скорость загрузки, затем визуальные эффекты |
| Twin / Talent | Больше свободы для выразительных сцен; читаемость, кнопки и выход из сцены на мобильном сохраняются |
| Клиентский проект | Отдельный профиль; по умолчанию мобильная версия и выразительность, с конкретными ограничениями |

## Как не потерять работу между чатами

GitHub хранит состояние работы рядом с кодом. Вход — `AGENTS.md`, затем `.twin/state.json`, затем результат и продолжение активной задачи. В реестре различаются: над чем работаем сейчас, какую версию сайта проверяем и что уже опубликовано.

Ветка — отдельная рабочая версия. Commit — сохранённый набор изменений. PR — предложение объединить изменения с другой веткой; создание PR само по себе ничего не сливает. Deployment — отдельное обновление доступного посетителям сайта.

Продолжать этот пакет нужно в **work/workflow-foundation-20261029** репозитория **AURRRUS/twin-web-concept**. Main и опубликованный сайт этим пакетом не обновляются. Простая команда «продолжи» срабатывает только тогда, когда новая сессия открыла правильный репозиторий и ветку.

Между GPT и отдельным чатом Codex нет подразумеваемой автоматической передачи. Если связь через инструмент не доступна, GPT сохраняет файлы в GitHub и выдаёт короткую команду, которую ты переносишь в Codex. Команда должна ссылаться на подготовленные файлы, а не требовать пересказать прошлую переписку.

Итог покажи после проверки». Условия показа/публикации команда берёт из актуальной задачи и действующих решений, не угадывает.

## Следующие шаги

**Первый — Twin.** Сделать точный край архитектуры и растительности в стыке hero/Journey, проверить сборку на desktop/mobile и штатный путь к действию. Открытый дефект — техническая работа команды; тебе не требуется объяснять, как рисовать alpha-маску. После проверки показать фактический результат и отличия.

**Второй — ПИН.** Найти и подключить его исходный репозиторий, синхронизировать актуальный визуальный профиль, пройти отдельный мобильный пакет с проверкой скорости и конверсии. Код ПИН текущим аудитом не проверен.

**Третий — повторяемость.** После двух реальных пилотов скорректировать правила по найденным сбоям и только затем переносить процесс на клиентские проекты. Массовая уборка старых файлов — отдельная задача с проверкой зависимостей и сохранением нужных источников.
