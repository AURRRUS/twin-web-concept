# WF-001 — единый workflow GPT Work → Codex для Twin

Дата: 29.10.2026. Статус: READY_FOR_IMPLEMENTATION. Режим: execute только инфраструктуры работы, инструкций и проверок. Сайт этой задачей не перерабатывать и не публиковать.

## 1. Результат

Новая сессия Codex по одному указателю восстанавливает текущую версию Twin, решения владельца, scope, материалы, открытые дефекты и следующий шаг. Web Production ведёт процесс; Frontend Engineer отвечает за инженерную композицию и реализацию; реальные исполнители Codex и отдельный reviewer оставляют проверяемые результаты. Типографика, визуальный контракт, тесты и публикация перестают жить в противоречащих копиях.

Общий процесс отлаживаем на двух самостоятельных проектах — Twin/Talent и PIN. Эта задача внедряет рабочий контур Twin. Исходный репозиторий PIN в текущем аудите не определён: не создавать его и не переносить туда Twin автоматически. PIN имеет отдельный следующий пилот.

## 3. Принятые владельцем правила

- Web Production — главный универсальный координатор. GPT работает в паре с владельцем; Codex ведёт исполнителей и отдельную проверку. Twin Site — адаптер проекта, а не второй общий координатор.
- Сохранять выбранный визуал подробно. Более сильную альтернативу показать рядом, объяснить механику и получить выбор до замены.
- Точность объекта неприкосновенна: архитектура, пропорции и все составляющие реального объекта. Responsive-подача может меняться в рамках выбранной иерархии.
- Владелец утверждает фундамент/типографику/сущности, ключевые welcome и конверсионные сцены, самый сложный переход, представительскую пробу графики перед серией и финал после команды. Не спрашивать заново об уже принятом; не отдавать ему расчёт каждой маски.
- PIN: mobile и скорость первыми. Twin допускает больший визуальный бюджет и несколько сильных эпизодов, сохраняя рабочий мобильный путь к действию. Клиентские профили определяются отдельно.
- Графику команда разбирает и производит самостоятельно по jobs. Перед серией — один сложный образец в desktop/mobile. Нет ограничения по времени — не разрешение на 30 неподтверждённых генераций. У каждого усиления есть цель, предел вызовов, осмотр между проходами и сохранённая лучшая версия.
- Motion обслуживает смысл и конверсию: числовые фазы, holds и выход, общий scroll budget, CTA/точки решения. Декоративные бесконечные галереи не являются целью.
- Technical PASS, visual verdict, owner approval и deployment — отдельные состояния. Разрешённый рабочий preview с дефектом не становится визуальным PASS.

## 4. Реализовать

### A. Однозначный вход и память

Свести изменяемые указатели в один канонический реестр. Входные Markdown-файлы ссылаются на него, а не копируют ветки/статусы. Явно различить активную работу WF-001, визуальную задачу candidate VIS-005, source/runtime version, опубликованный source и release target. Сохранить V1 отдельно.

Устранить найденные расхождения в пределах candidate: AGENTS/V2_START, `.twin/v2/project.json`, активная задача/run, decisions и handoff. Старые RESULT/QA не переписывать так, будто они проверяли новый код; пометить историческое состояние и связать с новым. В main подготовить только узкий входной указатель отдельным предложением, если это необходимо; не переносить туда исходники без задачи.

Зафиксировать наследование ENGINEERING.md и актуальных типографических ролей. У V2 один источник чисел; контракт и проверки используют его. Не менять CSS или шрифты сайта ради согласования документов. Если конфликт требует нового художественного решения, вынести конкретное расхождение, сохраняя действующий runtime.

### B. Совместимая поставка навыков

Принять приложенные версии Web Production и Frontend Engineer. Сверить `SKILL_BUNDLE.json`; сохранить текущие проектные overrides и лицензии. Обновить существующий skill manifest: источник/ревизия/хэши/override. Не скачивать latest при каждом запуске и не копировать весь каталог личных навыков.

Снять конкурирующее руководство из repo-копии Twin Site и маршрутизации: проектный адаптер отвечает за Twin-источники, бренд, маршруты и условия выпуска; Web Production — за общий процесс; FE — за инженерию. Другие personal skills этим заданием не редактировать.

### C. Реальные агенты Codex

Проверить runtime данной сессии. Запустить отдельного исполнителя ограниченного пакета и независимого reviewer после реализации. Записать фактические ID, scope, входную версию, выход и evidence; reviewer не автор изменения. Для дополнительных специалистов назначать конкретный предмет и владение файлами.

При поддержке текущим клиентом подготовить project-scoped custom agents с инструкциями из этого контракта; перед использованием проверить загрузку и фактический запуск. Не устанавливать новые MCP/плагины и не менять разрешения окружения. `.agents/skills` и UI-метаданные не являются запуском команды.

Если целевая среда не предоставляет подагентов/браузера, выполнить доступную работу, записать конкретное ограничение и отдельный handoff для независимой проверки в GPT Work. Не закрывать этот пункт самопроверкой под новым названием.

### D. Исполнимый статус и приёмка

Согласовать task/run schema и validator. Новый маршрутизатор использует schemaVersion=2, явные mode/targetStage и этап sample перед серией assets. Миграция существующего состояния делается по реальным свидетельствам: готовый файл не становится принятой сценой, необязательный job получает явный skip reason/evidence, отсутствующие проверки остаются pending/stale.

Scope подготовки не запускает реализацию/выпуск; review с отрицательным вердиктом может завершить read-only аудит, сохраняя дефекты. Review привязать к реальным runtime inputs fingerprint, версии контракта, reference, viewport/state и исполнителям. Не сверять только SHA отчёта и не принимать старый глобальный pass как проверку текущего сайта.

У разрешения публикации один канон. Сохранить ранее данное владельцем разрешение на рабочий V2 preview с известным mask-дефектом как отдельный режим; не использовать его для автоматической публикации в WF-001. Финальная приёмка остаётся у владельца. Проверка структуры JSON не доказывает визуальное качество или истинность записанных agent ID.

### E. Проверки актуального кода и документации

Добавить проверку согласованности входов/active task/branch/scope, типографического канона, schema, skill manifest и свежести review. Ошибочные фикстуры должны ломать проверку: stale pointer, ready вместо accepted для обязательного слоя, строковые motion phases, старый runtime, автор как независимый reviewer, неподтверждённый final release.

Расширить область запуска релевантного CI на фактические runtime-входы: public assets/fonts, package/lock/config и контракт, а также изменённые проверки. Проверить зависимости действующего `/v2/`: тест старого helper не объявлять проверкой нового ReferenceJourney. Сохранённые V1-тесты не удалять. Тест естественного выхода из scroll-сцены должен использовать пользовательский ввод, а не только scrollIntoView.

В этой инфраструктурной задаче не переписывать сайт ради удобства теста. Подготовить карту проверок и выполнить проверки изменённых механизмов; отсутствие браузерной проверки сайта обозначить честно. Не запускать дорогую полную матрицу на неизменном runtime только ради нового Markdown.

### F. Уборка без потери источников

Составить inventory `artifacts/`, docs snapshots, старых workflows/scripts: размер, назначение, потребители, оставить/архивировать/кандидат на удаление. Текущие эталоны, исходники и evidence действующих gates сохранить. Слепое удаление 483 MB недопустимо: сначала проверить зависимости и место сохранения. В рамках WF-001 выдать обоснованный план; не переписывать Git history и не удалять файлы массово.

## 5. Приёмка WF-001

1. Новая сессия/свежий отдельный агент по входной инструкции правильно находит task, branch, site candidate, принятые решения, открытый mask defect и режим выпуска. Результат воспроизводим без пересказа старого чата.
2. Один канон актуальных параметров и авторизации; стартовые документы не спорят с ним. V1 и V2 не перепутаны.
3. В репозитории доступны обе совместимые версии навыков, manifest проверяет их хэши, проектные overrides сохранены.
4. Исполнитель и независимый reviewer реально запущены и оставили отдельные результаты либо ограничение среды явно блокирует этот пункт. Одни имена ролей не достаточны.
5. Валидаторы проходят положительные и отрицательные сценарии выше. Приложенные unit tests навыков проходят; новые проверки тоже проверены.
6. Существует карта текущего route→component/controller→contract→test; область каждого PASS названа точно.
7. Runtime `src/`, `public/`, шрифты, тексты и дизайн не изменены этим пакетом. Генерация и deployment не запускались.
8. RESULT содержит changed files, source version, фактические команды, review, ограничения и следующий этап. Handoff указывает следующий конкретный шаг, не «всё готово».

В завершение сохранить результат в ветке и обновить draft PR. Не merge автоматически. Вернуть ссылку на diff/PR, фактический статус каждого пункта и короткую команду продолжения.
