# Twin — единое ТЗ на последовательную доводку существующего сайта

Версия 1.0 · 03.11.2026 · ведущий: Web Production · инженерный соавтор: Frontend Engineer

**Назначение:** одно задание для команды GPT/Codex. Выбрать и закрепить одну существующую базу, использовать лучшие пригодные решения прежних версий и доводить тот же сайт ограниченными пакетами. Первый исполнительный пакет — только шапка, первый экран, переход и второй экран Journey. Остальная страница здесь описана как очередь работ, а не разрешение переделать её сразу.

ТЗ объединяет независимые заключения Web Production и Frontend Engineer от 03.11.2026. Сравнение версий и мобильного размера 390×844 выполнено; полная техническая регрессия всех версий не заявляется. Производство новой графики и реализация этого ТЗ при его подготовке не запускались.

Маска показывает существующие пиксели; нужную, но отсутствующую террасу она не создаёт. Число прогонов генерации, успешный build и отсутствие overflow не доказывают соответствие образцу.

## 4. Архитектура доработки

- Вход страницы: `src/pages/v2/index.astro`.
- Journey и нижние секции: `src/components/v2/ReferencePage.tsx`.
- Верхняя связка: `src/styles/v2/hero-journey.css`.
- Общая визуальная система V2 и нижние секции: `src/styles/v2/reference-page.css`.
- Действующие предметные компоненты: `src/components/ProductDemo.tsx`, `Composition.tsx`, `ContactForm.tsx`.
- Состояния/контент: действующие `src/lib/config.ts`, `salesStoryContent.json`, `compositionContent.json`, `componentDialogs.json` и связанные данные. Медиа-пути обслуживает `src/lib/paths.ts`.
- Материалы верхней сцены хранить рядом с текущим `public/media/top-v2/`, не дублировать основной hero под каждой итерацией. Для новых файлов зафиксировать происхождение, размер, canvas, bbox, anchor, назначение и статус принятия в сцене.

Текущий маршрут рендерится через `index.astro` → `ReferenceJourney`/`ReferenceRest`. Старые `FullPage.tsx`, `Journey.tsx`, `full-page.css`, `site.css` не выбирать параллельным корнем реализации. Сохранить существующие компоненты и их поведение. При переносе удачного решения переносить только необходимую разметку/стиль/ассет, с записью донора и причины. Не копировать собранные JS-bundles или весь CSS старого сайта. При первом фрейме разрешить фактическое расхождение max-width:1840px в общем CSS против1728px в старом ENGINEERING. Для первых экранов зафиксировать одно выбранное значение и поля в scoped-контракте; нижнюю страницу на этом этапе не мигрировать. Одна роль текста и один параметр сцены имеют один источник; не наслаивать бесконечные поздние overrides. Локальное исправление не должно менять нижние блоки через общий каскад.

## 6. Подробное задание на этап 1

### 6.1. Границы

Включено: шапка, hero, полный переход и весь Journey с четырьмя режимами; desktop/mobile и их адаптив, штатные ссылки, клавиатура, обычная прокрутка. Нижняя граница — начало существующего тёмного демо. У границы проверить отсутствие разрыва; само демо на этом этапе не перестраивать.

Сохраняются: смысл и актуальные тексты, реальный морской исходник, геометрия здания/этажи/фасад/балконы, функции четырёх режимов, брендовые файлы, нижние компоненты, V1. Не вводить новый параллакс, WebGL, новый стек, новую воронку или новую серию картинок.

### 6.2. Сначала точная композиция в существующей сцене

Зафиксировать контрольные desktop 1440×900 и mobile 390×844. Для каждого подготовить целостный фрейм двух экранов с настоящими шрифтами и текстами: границы hero/Journey, фото/море/архитектура, H1/H2, CTA, четыре режима, рамка активной медиа. Сначала показать выбранное первое состояние «Локация и инфраструктура», затем проверить остальные три. Высота длинного фрейма определяется композицией и содержимым: не требуется уместить оба экрана в900px. Линиями обозначить границы viewport900/844px, чтобы видеть реальный первый экран и положение перехода. Фреймы и контрольные PNG относятся к той же странице, не являются отдельными версиями сайта.

Frontend записывает измеримые параметры: viewport; холст; crop/anchor/transform; видимый bbox основных объектов; ширина текстовой группы; размеры шрифта/leading/tracking; расстояния между группами; положение CTA и медиа; границы декоративного перекрытия. Для каждого значения указать «из источника», «измерено по растру» или «инженерное предложение». Оценку по изображению не выдавать за точный исходный kerning.

Высоту hero не заимствовать из неудачной пробы только потому, что там нет overflow. В C и D она существенно различалась: `min(72vw,1120px), min-height780px` против `clamp(650px,48vw,930px)`. Цель — правильное отношение изображения, текста и следующей сцены, а не автоматическое утверждение любого из этих CSS-чисел. Обещание и CTA не должны оказаться на случайно подошедшем белом клине.

### 6.3. Графическая подготовка верхнего перехода

Подготовить **один необходимый графический узел** под камеру выбранного берегового hero. Требуется связующая передняя архитектурная поверхность/терраса; точная маска правого края сама по себе её не заменяет. Использовать пригодные реальные части исходника и, где нужны новые пиксели, локальный композит/дорисовку передней зоны. Не менять весь курорт ради удобного силуэта. Защищённое здание не перегенерировать. Если новый передний план меняет утверждённый визуальный характер, показать это как предмет выбора до внедрения.

| Слой | Способ и выход |
|---|---|
| Основной морской фон | Существующий hero без разрушительной перезаписи; одна система camera/crop/anchor |
| Архитектурный передний pass | Подготовленный фотографический слой с правильной перспективой, материалом, освещением и опорой; полный согласованный холст и offsets |
| Предметная alpha/matte | Край архитектуры/растительности/тонких деталей. SVG допускается для действительно прямых жёстких граней; листья, стекло и полупрозрачные края требуют подходящего matte |
| Светлая поверхность Journey | CSS/SVG-контур, согласованный с предметным pass; не произвольный треугольник, изображающий отсутствующий фотографический объём |
| Тени | Одна согласованная контактная/окружающая тень. Не накладывать вторую поверх уже запечённой без необходимости |
| Тексты, навигация, CTA, режимы | Настоящие DOM-элементы с проектными шрифтами и отдельной сеткой |
| Изображения Journey | Существующие четыре утверждённых файла, отдельные от архитектурного фона; без AI-надписей и псевдоинтерфейса |

Все части имеют общий масштаб, камеру, anchor и свет. Tight-crop-файлы без offsets не принимать. Не прятать дефект архитектурного края размытием/feather. Новых пикселей за физическим концом исходника нет: либо подготовить материал, либо изменить конкретную границу композиции до верстки, сохраняя замысел. Отсутствующий материал не выдавать за завершённый CSS-приём.

На mobile сделать свою композицию/crop/якорь и при необходимости отдельный производный передний слой. При общей камере корректную alpha можно переиспользовать; отдельная маска на каждую ширину не обязательна. Широкую desktop-террасу не сжимать целиком в 360px. Сохранить крупную узнаваемую архитектуру и море, читаемые тексты и связь со вторым экраном.

Не запускать серию, пока один сложный узел не принят в сцене. План этапа 1 — один графический job, первоначальная попытка и при необходимости одна адресная корректировка. Усиление/апскейл назначать только при видимом дефекте детализации на конечном размере. Если за две попытки улучшения нет, остановить тот же метод, назвать неверное допущение и изменить диагностику. Не расходовать дальнейшие вызовы на похожие неудачные варианты.

### 6.4. Типографика и композиция

| Роль | Текущая инженерная отправная точка desktop / mobile |
|---|---|
| H1 | RF Dewi Expanded Bold700, 58/68px · 30/38px, tracking0 |
| H2 | Тот же реальный Expanded Bold700, 46/56px · 28/36px, tracking0 |
| Подзаголовок режима | RF Dewi Bold700, 24/32px · 22/30px |
| Основной текст | RF Dewi Regular400, 20/30px · 17/26px |
| Управление | RF Dewi Semibold600, 17/26px · 16/24px |

Это наследуемые числовые роли, а не запрет исправить обнаруженную плохую композицию. Сначала проверить реальный файл шрифта, начертание, загрузку, ширину блока, переносы, leading и соседние массы. Не подбирать похожий шрифт. Изменение роли должно быть обосновано фреймом и затем записано в одном каноне. Наблюдаемый старый tablet40/68 не превращать автоматически в целевую типографику. Не использовать synthetic bold, scaleX, отрицательные поля или переполнение как способ уместить неверную текстовую группу.

H1, изображение и CTA образуют один входной рассказ. H2 — компактная смысловая масса, не случайная широкая строка над всей сценой. Journey сохраняет крупную медиа справа и понятный выбор слева; активная карточка получает насыщенный бронзовый вес по reference со светлым читаемым текстом, а не теряется среди соседних; соответствующие цвета брать из палитры V2 и проверять контраст всех вложенных подписей. Реальный UI может быть прямоугольным; вся окружающая сцена при этом не должна превращаться в обычную коробку со скриншотом.

В мобильной версии читаемость и предметный кадр проектировать вместе. Мелкие надписи внутри большого desktop-скриншота не считать читаемым мобильным интерфейсом. При необходимости показать осмысленную деталь изображения и доступ к полной демонстрации, не вырезая необходимые доказательные элементы без объяснения.

### 6.5. Вёрстка, адаптив и движение

Собрать статичную композицию в существующих компонентах. Проверить 1440×900 и 390×844, затем 1366×768, 1920×1080, 360×800, промежуточные ширины768/1024/1099/1100. Изменение ширины не должно разъединять слои. Учитывать ширину scrollbar: viewport100vw и ширина контейнера могут различаться.

До визуального соответствия статичной сцены не добавлять анимацию. Существующий sticky проверять после статики: fit по высоте, обычный scroll/touch, прямой выбор каждого режима, обратный ход, повторный вход и свободный выход после последнего состояния. Не перехватывать wheel и не считать прогресс количеством wheel-событий. При недостатке высоты/mobile/reduced-motion — доступный нормальный поток. Числовую длительность/scroll distance и фазы задавать по смыслу и работающей пробе, не наследовать 1800px как доказанно правильный темп. Последовательность четырёх режимов не становится обязательным путём покупки.

### 6.6. Первый показываемый результат

К владельцу передать ту же работающую страницу с первыми двумя экранами, а также:

- desktop и mobile кадры целиком с настоящими шрифтами и загрузившимися изображениями;
- одинаковый участок reference и результата рядом, в сопоставимом масштабе;
- крупный кадр стыка/краёв и краткое «что изменено / что осталось»;
- реально открываемый способ просмотра: проверенный URL или приложенный самодостаточный файл. Фраза «открыл в моём браузере» без доступа владельца не является доставкой.

Не выдавать незагруженные шрифты, временные fade-состояния, пустой iframe или снимок другого кандидата за результат. Если локальный просмотр владельцу недоступен, координатор сам готовит доступную выдачу; пользователь не должен разбираться в среде или искать файлы.

## 7. Визуальная приёмка — обязательная работа команды

Исполнитель сначала исправляет собственные дефекты. Затем отдельный фактически запущенный reviewer получает только цель, reference, контракт и кандидата, без оправданий автора. Web Production возвращает дефекты исполнителю. Владелец принимает художественное решение после команды, а не служит первым проверяющим явных ошибок.

| Проверяемая сторона | Условие передачи владельцу |
|---|---|
| Массы и пропорции | Главный объект, ширина текста и размер UI соответствуют согласованному фрейму. Нет подавляющего центра/микроподписей и случайно огромных пустот |
| Направляющие и интервалы | Связанные группы выровнены, края и поля имеют общий ритм; нет случайных смещений и пересечений |
| Типографика | Реальные проектные шрифты загружены; размеры, начертания, переносы, leading и tracking проверены визуально. Длинное слово не маскируется отрицательным margin |
| Материал и перспектива | Передний план имеет опору/перспективу и согласованный свет; маска не выглядит геометрическим вырезом вместо объекта |
| Crop и слои | Нет двойного здания, смещения, шва, ореола, обрыва или отсутствующего фона; слои не ловят клики поверх управления |
| Смысл и действие | Сразу видны обещание, демонстрация и следующий CTA; эффекты не блокируют действие |
| Mobile | Сцена перекомпонована, а не просто уменьшена; текст/управление читаются, объект узнаваем, все режимы доступны |
| Доставка | Владелец может открыть и увидеть конкретный проверенный кандидат |

Для каждого пункта записать: reference/candidate/viewport/state → наблюдаемое отличие → исправление → результат повторной проверки. Новые параметры и допуски фиксируются до подгонки кода, а не меняются после осмотра ради PASS. Единый выдуманный «процент сходства» не использовать.

Вердикты: `rebuild` — не совпали композиция или ключевой материал; `fix` — локальные дефекты; `recapture` — нет нужного состояния; `ready-for-owner-review` — существенные расхождения устранены. Отдельно хранить technical checks и решение владельца. Build, скриншоты и JSON сами по себе не дают визуальной приёмки. Не передавать явно кривую сцену с формулировкой «в целом готово, осталось немного маски».

После двух безрезультатных циклов по одному дефекту прекратить повторение. Координатор определяет, проблема в исходнике, модели сцены, каскаде, геометрии или инструменте; предлагает конкретную коррекцию подхода. Критерий качества не снижать молча до простых прямоугольников.

## 8. Проверки последующих блоков

**Единая основа:** все шесть названий должны читаться без zoom. Для проектирования этапа2 принять ориентиры: названия18–20px desktop, пояснения15–16px; mobile названия≥17px, пояснения≥15px. Это предложенные рамки, не ранее утверждённые цифры. Массу центра определять по видимому bbox, а не размеру прозрачного файла; ориентир при первом фрейме — центр около≤44% ширины схемы, боковые колонки около≥22% каждая. Если выбранный объект/реальные тексты требуют другого решения — обосновать его на фрейме. Линии не пересекают текст; подписи не выглядят приложением к модели.

**Четыре канала:** desktop должен показывать четыре содержательных слоя и явный активный канал. Задние панели не заменять пустыми полосками; название, изображение, навигация и стрелки синхронны. Перспектива и глубина рассчитываются совместно; подписи кодом и остаются читаемыми. На mobile допускается своя композиция с одной активной сценой и четырьмя явными выборами. Смена канала не прыгает высотой страницы, лица/ключевые элементы не обрезаются, следующий блок свободно достижим.

**Демо, качества, запуск, контакт:** сравнивать каждый целиком со своим участком reference и отдельно проверять главное материальное отличие. Исправить цвет фона недостаточно для предметной сцены. Новый ракурс модели, ночной фасад, островное основание или иной центральный объект — отдельный материал/решение, а не скрытая CSS-имитация.

Отклонение означает исправление этого же пакета в этой же базе. Принятые desktop/mobile фреймы, слои, типографика и параметры затем становятся baseline; следующие пакеты не должны их незаметно менять.

## 10. Техническая проверка, сохранение и публикация

Для этапа1 обязательны проверка типов, сборка V2, проверка затронутых контрактов и browser-проверка реального `ReferenceJourney`, а не старого helper. Использовать проектные команды, проверив их фактическую конфигурацию: `npm run typecheck`, `npm run build:v2`, `node scripts/workflow-check.mjs`; маршрут и набор QA-сценариев должны соответствовать текущему кандидату. Полную регрессию нижних блоков не повторять после каждой правки маски; выполнить адресные проверки и осмотр входа в третий блок.

Известные технические нюансы предыдущей пробы: импорт несуществующего типа V456Frame локально заменён на ReturnType без изменения поведения; для чистой сборки требуются генерируемые tokens; добавление прежней `top-v2/opening-terrace-mask.svg` в whitelist `scripts/build-v2.mjs` осталось незакоммиченной локальной правкой предыдущей сессии и не считается доставленным. Проверить fresh checkout; перенос старой ненужной маски не требуется. Новые материалы `top-v2/` должны попадать в отдельное дерево V2 через `scripts/build-v2.mjs`. Переносить только действительно нужные исправления после проверки свежей базы. Проверить конечные HTML/CSS-зависимости, включая SVG-маску, а не только факт успешного bundling. Локальные правки dev-host не переносить вслепую, если рабочая среда другая.

Сохранять изменения исходников и результаты в основной рабочей базе, с ясными донорами и областью правок. Удаление старых веток, массовая чистка evidence и перенос репозитория ZIP не входят в задание. Публичная загрузка и deployment — отдельные действия по действующим разрешениям; прежний отказ записи VIS-006 не обходить. Подготовка этого ТЗ не означает публичную публикацию, слияние или обновление сайта. Если запись ограничена, сохранить точный пакет локально и объяснить конкретное ограничение; продолжать разрешённую работу над сценой.

При передаче этапа сообщать только: что исправлено в той же версии, что проверено, какие существенные отличия остались, где открыть результат. Нельзя объявлять готовность всего сайта после приёмки двух экранов, демонстрационную форму — работающей системой заявок, а текст на образце — доказанным коммерческим обещанием.

## 11. Первый рабочий ход исполнителя по этому ТЗ

1. Web Production восстанавливает указанную единственную базу и активирует ограниченный пакет этапа1.
2. Frontend подготавливает измеримые desktop/mobile фреймы и точный заказ одного архитектурного переднего узла с защищённым hero.
3. Команда создаёт/собирает контрольную графику в контексте двух экранов, проводит внутреннее сравнение и показывает владельцу конкретный сложный узел до серии.
4. По выбранной композиции доводит те же два экрана в том же V2, проверяет статичность, адаптив, затем существующее движение и четыре режима.
5. Независимый reviewer возвращает дефекты до готовности показа. Владелец принимает результат этапа1. После принятия зафиксировать baseline и остановиться; остальная очередь запускается отдельной командой владельца, без составления им нового технического задания.

**Короткая команда исполнителю:** «Выполни этап1 по этому ТЗ в выбранном V2. Сам восстанови контекст, подключи исполнителя и независимого проверяющего. Остальные блоки пока не меняй. Покажи проверенный результат этой же версии».
